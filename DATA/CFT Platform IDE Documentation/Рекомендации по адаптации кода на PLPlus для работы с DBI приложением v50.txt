1. SQL/DML
Обе СУБД поддерживают ANSI SQL в соответствии со спецификации 2012, но есть нюансы, которые следует учитывать при разработке. 
В данном разделе по большей части приведены рекомендации по миграции кода в ANSI SQL.

1.1. Outer join
Oracle оператор (+) в ANSI не поддерживается. Далее нельзя использовать 
PLPlus параметризацию типа соединения (true/false) в where. Вместо этого нужно использовать явные left/right join on. 

Пример:
	for (select x(
		x.[DOCUMENT]: DOC
		, case when md.[QUIT_DOC] is not NULL then 1 else 0 end: QUIT_DOC)
		in folder.[DOCS_IN_FOLD] left join (::[MAIN_DOCUM]: md) on x%id = md%id 
		and x.[DOCUMENT]%class = ::[MAIN_DOCUM]%class
		order by 2 desc)
	loop

Выявление:
Трансляция с параметрами APPLICATION.DBI = 1 and PLP_GENERATE_ANSI_JOINS = 1 и анализ невалидных oracle packages, а также проверка по кодам запросов. 

1.2. Ограничение выборки 
Ранее для ограничения выборки использовалась псевдоколонка “rownum”. В PostgreSQL таких псевдоколонок нет. Вместо этого нужно использовать конструкцию 
- PLPLUS fetch X
- Трансляция fetch first X rows only
Дополнительно требуется оценка влияния изменения кода на планы запросов Oracle. 

Некоторые отличия fetch от rownum

* order by - сортировка применяется ко всей выборке, потом ограничивается количество строк. 
Запрос fetchРезультатЗапрос rownumРезультатselect	p(p%id) in ::[PRICE_LIST] all
order by p%id desc fetch 1
into	vRef;16760145966select	p(p%id) in ::[PRICE_LIST] all
where rownum=1
order by p%id desc
into	vRef;2052810
* агрегатные/оконные функции: sum, min, max, avg, count, listagg и т.д. first_value/last_value/... over ...- обрабатывают весь объем данных, только потом ограничивается количество строк. В некоторых случаях это будет требовать подзапроса с ограничением выборки, а далее применения над ним самой функции.
Запрос fetchРезультатЗапрос rownumРезультатselect	p(count(p%id)) in ::[PRICE_LIST] all
fetch 1
into	vCount;79select	p(count(p%id)) in ::[PRICE_LIST] all
where rownum=1
into	vCount;1* разное поведение и различные планы запросов

 
Пример:
	select	p(p)
	in		::[PRICE_LIST] all
       where	p.[CODE] = upper(pCode) fetch 1
into	vRef;
	
       v_var := 2;
	select	p(p)
	in		::[PRICE_LIST] all
	where	p.[CODE] = upper(pCode) fetch v_var
	into	vRef;

Для сдвига выборки используется конструкция offset on X
Пример:
	select	p(p)
	in		::[PRICE_LIST] all
       where	p.[CODE] = upper(pCode) offset on v_var
into	vRef;
Выявление: 
проверка по кодам запросов 

Примечание: В ТЯ 7.6.10.6 поддержана возможность указания размера выборки через параметр (bind переменную).


1.3. UDF

Реализовано в ТЯ 7.6.10.1

Ограничения
1. Не рекомендуется использовать UDF для представлений.
2. Не поддерживается работоспособность любой функциональности, кроме визуализации, по колонкам, использующим UDF (фильтры, сортировки, статистика, доступ по реквизиту, переходы по ссылкам и т.д.)
3. Не поддерживается трансляция бизнес-кода в серверный код (server side logic), поэтому нельзя использовать функции PLPlus бизнес-кода в SQL за исключением использования функциональных реквизитов и функций как выражений выборки в основном запросе со следующими ограничениями: 

Для операций: 
* вычисляемые колонки могут быть использованы только в селект-листе запроса верхнего уровня
* Невозможно использование в запросе верхнего уровня с UNION
* Невозможно использование в подзапросах
* Невозможно использование в выражениях 
* Невозможно использование функций, определенных в самой операции (Есть задачи на развитие)
* если в списке параметров функций используются только модификаторы для источников данных запроса, то такая колонка не будет определена как вычисляемая, будет сгенерировано обращение к функции пакета
Для представлений:
* не работает сортировка - будет выдана ошибка “имя_колонки не поддерживает сортировку” 
* не отработает фильтр - будет выдана ошибка “фильтрация данной колонки не поддерживается”
* для колонки с типом timestamp не определяется тип в IDE, т.е. невозможно штатно задать формат даты
* статистика по вычисляемой колонке не поддерживается - будет показана ошибка в АРМе Навигатор
* для вычисляемых колонок-массивов не поддерживается подсчет точного количества записей
* не поддерживается вычисление колонок REF$ (нет корректной диагностики ошибки, представление не будет работать корректно)
* не поддерживаются колонки с базовыми типами "OLE" и "TABLE" 
* не будет работать доступ по реквизиту для вычисляемой колонки
* нельзя в выборке из представления обращаться к UDF колонке
Так нельзя:
for (select acc(
			acc.[MAIN_V_ID]	:	acc_num
			,f.a('И'||acc, p_date_end) : saldo
		) in ::[AC_FIN]
			where acc.[MAIN_USV] = p_usv	
	)loop	
		str := acc.acc_num ||'='||acc.saldo;
end loop;

Так можно:
	for (select acc(
			acc	: acc,
			acc.[MAIN_V_ID]	:	acc_num
		) in ::[AC_FIN]
			where acc.[MAIN_USV] = p_usv	
	)loop	
		str := acc.acc_num ||'='||f.a('И'||acc.acc, p_date_end);
end loop;

Выявление:
Через плагин PLPCheck, проверки UDF, UDF_IN_FILTER_FORMULA, CONSTANT_ORDER_BY_ON_UDF, DISTINCT_UDF, PURE_UDF, FUNC_ATTR_DEREFERENCE
      
1.4. Служебные слова PostgreSQL 
Нельзя использовать служебные слова для установки синонимов (aliases)
Проблема решена средствами ТЯ. В прикладном коде исправлений не требуется. 

1.5. Приведение типов
      * Только для СУБД PostgreSQL

 У Oracle и PostgreSQL разные:
* правила неявного приведения типов данных;
* функции явного преобразования типов.
Поэтому необходимо писать код, в котором используются совместимые типы данных или их явные преобразования. 

Ниже приводятся только основные причины и рекомендации. Список будет пополняться по мере выявления новых причин.

Частично различия в поведении будут устраняться с помощью реализации локальных операторов в PostgreSQL , которые для обеспечения совместимости будут поставляться либо через реализацию прикладных функций для PostgreSQL, либо через расширение PostgreSQL

Примеры:

* сложение числа со строкой в общем случае несовместимо 

Oracle 
SQL> select c_code, c_code + 1 from "Z#DEPART" where id = 22854243;

C_CODE                 C_CODE+1
-------------------- ----------
041                          42

   PostgreSQL
cft14=# select c_code, c_code + 1 from "Z#DEPART" where id = 22854243;
ERROR:  operator does not exist: character varying + integer

1.8. Иерархические запросы
* Только для СУБД PostgreSQL

Для реализации иерархических выборок использовался синтаксис «connect by». Начиная с ТЯ 7.6.9.2 для той же цели нужно использовать CTE (WITH [RECURSIVE]) т. к. данная конструкция описана в ANSI SQL и поддержана в PLPLUS

Ограничения:
1. Иерархические запросы по метаданным под запретом. Проверка в PLPcheck
2. Внутри выражения WITH нельзя использовать колонку вышестоящего запроса или колонку таблицы, которая соединяется на уровне конечного запроса with. Например, нельзя сделать колонку-подзапрос, которая зависит от данных основного запроса. Проявляется в SQL ввиде ошибки компиляции.
3. Порядок выборки данных отличается от connect by. 
4. Нет аналога nocycle. Ограничение от зацикливания надо указывать в секции where


Пример из DEPART.LIB
Было  
	select d_(d_.ID:D_ID) in
    	(select d(d%id:ID,d.[HIGH]:HIGH) in ::[DEPART] connect by d%id=prior d.[HIGH] start d%id=dep)
	where d_.[HIGH] is null and rownum<2 into high_dep;
	
       Стало 
	with recursive t(id, high) as
	(select x(x%id:id, x.[HIGH]:high) in ::[DEPART] where x%id = dep
	union all
	select x(x%id:id, x.[HIGH]:high) in ::[DEPART] join (t:t2) on t2.high = x
	) select t1(t1.id) in t where t1.high is null fetch 1
	into high_dep;

проверка по кодам запросов, PLPcheck

1.24. DDL  
* Только для СУБД PostgreSQL

В PostgreSQL в отличии от Oracle, при создании объекта БД без указания схемы , объект будет создан на схеме,  указанной первой в search_path.  

При выполнении команды модификации/удалении объекта без указания схемы, поиск также будет производиться на схеме, указанной первой в search_path. Если не будет найден, PostgreSQL сгенерирует ошибку.

Настройка search_path частично определяется ЦФТ, частично банком и совершенно точно, что схема с прикладными данными APP будет ниже в списке приоритетов, чем, например, схема SYS и BANK.  

Поэтому, при выполнении DDL  из прикладного кода, обязательно указывайте имя схемы. 
Пример - create table app.z#.....  

Имя схемы app может быть изменено, поэтому использовать это имя как константу нельзя.
      
Для получения имени схемы по имени ТБП и имени sequence были созданы функции в ::[RUNTIME].[DB]

public function get_scheme_tbp
/* Получение информации о схемах, где расположен ТБП. */
							( p_tbp in varchar2(16)
							/* Короткое имя ТБП */
							)
/* Возвращается массив имен схем */
       return ::[RUNTIME].[RTL].string_table;
       
public function get_scheme_sequence
/* Получение информации о схемах, где расположена последовательность. */
							( p_seq varchar2(100)
							/* имя последовательности */
							, p_db_type in  varchar2(100) default null
/* БД в которой искать схему, по умолчанию это БД где находится ТБП SYSTEM*/
							)
/* Возвращается массив имен схем */
       return ::[RUNTIME].[RTL].string_table;
      
Для Oracle функция будет всегда возвращаться схема хранения данных, как правило это IBS.
Для PostreSQL  - будут возвращаться схемы, на которых были обнаружены указанные вами объекты.
Если функция вернет более 1 схемы, то скорее всего в прикладном коде надо будет генерировать ошибку, т.к. будет нельзя понять, где потребуется создавать/модифицировать/удалять объект.

       lcvStringEmpty varchar2(32767) := null;

       correct_var.MY_FIELD := '';
       
       debug_pipe(' length(correct_var.MY_FIELD ) '||length(correct_var.MY_FIELD )|| ', (correct_var.MY_FIELD is null) = '||(correct_var.MY_FIELD is null) ,0);
end;

2.2. Date
      * Только для СУБД PostgreSQL
      Функциональность включена в расширения dbi-funcs  версии 1.13  

Тип DATE в PostgreSQL не хранит время. В связи с этим, принято решение по миграции данных из Oracle типа DATE в PostgreSQL в тип TIMESTAMP(0).  Были созданы прикладные операторы, которые обеспечивают выполнение сложения/вычитания с числом для типа TIMESTAMP(0). 

Например:
test=# select c_stamp,c_stamp + 1 res1, c_stamp - 2 res2 from "Z#RECORDS" fetch first rows only;
       c_stamp       |        res1         |        res2
---------------------+---------------------+---------------------
 2002-07-19 23:59:59 | 2002-07-20 23:59:59 | 2002-07-17 23:59:59

Так же, в технологическом ядре реализована возможность использования типа interval. Такие варианты тоже будут работать

Например, оба варианта будут работать:
	for a in ::[RECORDS] all where a%collection = p_coll 
	and a.[DATE] + 1> sysdate order by a.[STAMP] desc

	for a in ::[RECORDS] all where a%collection = p_coll 
	and a.[DATE] + interval('1', 'DAY') > sysdate order by a.[STAMP] desc

На текущий момент, есть различия в поведении при вычитании PLPlus типов DATE.	Для Oracle это будет DATE-DATE=INTEGER
	Для PostgreSQL TIMESTAMP-TIMESTAMP=INTERVAL

Для решения данной задачи следует использовать в PL+ функцию to_number(to_char()) 

Пример использования
…. to_number(to_char(date1-date2)) ….

 Внимание! При помещении средствами платформы данных с миллисекундами в поле TIMESTAMP(0), PostgreSQL  производит округление до секунд. Для Oracle в поле типа date миллисекунд попросту нет, значение сохраняется только до секунд включительно. Это необходимо учитывать в разработке, отсекая миллисекунды на прикладном уровне для получения идентичных данных в разных БД. Пример различия , 
код cref.[CH_DATE] := to_timestamp('31/12/10 23:11:59.999', 'dd/mm/yy hh24:mi:ss.FF9'); 
где @name('Дата и время')  CH_DATE [DATE_TIME];

2.6.2. Уникальные индексы 

В PostgreSQL null значения входят в состав индекса. Это порождает некоторое отличие в поведение уникальных СОСТАВНЫХ индексов. 
Когда все ключевые поля составного уникального индекса = NULL, то при повторной вставке записи получим  исключение в PostgreSQL. В Oracle исключения не будет, вставка возможна.
Когда часть ключевых полей = NULL, при вставке аналогичной записи получим исключение. Поведение в PostgreSQL и Oracle одинаково.

Пример различия и одинакового поведения:
PostgreSQL
CREATE TABLE app."KTST" (
	c_vek numeric NULL,
	c_num numeric null 
);
/* платформа создает уникальные составные индексы с параметром NULLS NOT DISTINCT  для получения максимальной похожести на поведение Oracle */
CREATE UNIQUE INDEX "IDX_KTST" ON app."KTST" USING btree (c_vek, c_num) NULLS NOT DISTINCT;
commit;
insert into app."KTST"  ( c_vek,c_num ) values  (null , null);
insert into app."KTST"  ( c_vek,c_num ) values  (null , null);
//получаем исключение SQL Error [23505]: ERROR: duplicate key value violates unique constraint "IDX_KTST"
  Подробности: Key (c_vek, c_num)=(null, null) already exists.
  В Oracle ошибки не будет.
Rollback;
insert into app."KTST"  ( c_vek,c_num ) values  (1 , null);
       insert into app."KTST"  ( c_vek,c_num ) values  (1 , null);
// SQL Error [23505]: ERROR: duplicate key value violates unique constraint "IDX_KTST"
  Подробности: Key (c_vek, c_num)=(1, null) already exists.

Oracle
CREATE TABLE KTST (
	c_vek numeric NULL,
	c_num numeric null 
);
       CREATE UNIQUE INDEX IDX_KTST ON KTST  (c_vek, c_num);
       insert into KTST (c_vek,c_num ) values (null, null);
       insert into KTST (c_vek,c_num ) values (null, null);
       // ошибки нет
		insert into KTST (c_vek,c_num ) values (1, null);
		insert into KTST (c_vek,c_num ) values (1, null);
		//ORA-00001: нарушено ограничение уникальности (IBS.IDX_KTST) 

Данное различие в работе уникальных составных индексов необходимо учитывать при адаптации функциональности к DBI 

Поведение уникальных индексов, состоящих из одного поля, одинаково в Oracle и PostgreSQL.

Внимание! Если в таблицах уже есть дубликаты записей с null в ключевых полях и планируется переходить на PostgreSQL, необходимо избавиться от дублей. 


2.6.3. GINИндексы с ключом большого размера

В общем случае, в PostgreSQL размер строки BTREE индекса не может превышать 2704 байт. 
Ограничение в 2704 байта справедливо как для составного индекса, так и для индекса на одно поле.
Ошибку можем получить, когда:
* Данные уже находятся в таблице и создаем индекс 
* Индекс уже существует, и мы добавляем/меняем строку таблицы.
Ошибка проявляется, как исключение БД с текстом 
“… index row size … exceeds btree version 4 maximum 2704 for index …”

Нет прямой корреляции между количеством символов индексируемых полей и размером 2704  байта. Потому что на размер строки индекса влияют два фактора:
* Текстовые поля по умолчанию сжимаются алгоритмом lz4 или pglz
* Символы хранятся в  UTF-8. Поэтому символ может занимать от 1 до 4 байт

Поэтому в зоне риска находятся все индексы с размером суммы текстовых полей более 676 символов ( 2704/4 ). Чем больше сумма, тем больше риск.  Полями других типов данных пренебрегаем из-за их небольшого влияния.

Например, в 2704 байта поместится строка из:
* 1 300 рандомных букв только русского алфавита
* 150 000 букв “w”

Вариантами решения могут быть:
* Уменьшение размера поля
* Исключение из индекса неиспользуемых полей
* Переход на GIST индекс. Он отодвигает ограничение по размеру с 2704 байт до 8191 байт. Он быстрее при поиске, но вставка данных будет медленнее. Также GIST индекс не поддерживает уникальность. Синтаксис описания находится во встроенной справке А2 по пути CFT Platform IDE Documentation > Элементы прикладной модели > Индексы > Аннотации @property для индекса и колонок индекса. 
Обратите внимание, что если вы планируете использовать like при работе с GIST индексом, необходимо в его описании указать опцию gist_tgm_ops. 
* Переход на GIN индекс. Он убирает ограничение по размеру индексируемого поля. Он еще быстрее при поиске относительно GIST индекса, но еще медленнее при вставке. Вставка в GIN медленнее чем в GIST от 2 до 10 раз. Размер индекса будет больше чем GIST от 1.2 до 3 раз.  GIN индекс не поддерживает уникальность. При его описании необходимо указывать опцию gin_tgm_ops, пример
class TST; 
@property('PG.METHOD_CLAUSE:=GIN') 
index IDX_Z#TST_GIN { 
@property('PG.OPCLASS:=gin_trgm_ops') 
CODE; 
}
* Ничего не делать, если данные таковы, что размер строки индекса  не превысит 2704 байта
* И т.д.

Выявление:
Через плагин PLPCheck, проверка INDEX_LENGTH

2.8. Временные таблицы (TEMP TABLE)
Работа с временными таблицами в Oracle и PostgreSQL различается. Кроме того, использование временных таблиц в OLTP системе на базе PostgreSQL оценивается как ошибка дизайна, приводящая к pg_catalog bloat. По этим причинам необходимо избавиться от временных таблиц в модели данных.  Альтернативой может служить varray, см. п. 5.2.

В случаях крайней необходимости временные таблицы допустимы для использования, но при выполнении следующих условий. Следует иметь в виду, что в PostgreSQL отсутствуют глобальные временные таблицы. Каждую временную таблицу перед использованием необходимо создать внутри сессии. Начиная с версии ТЯ 7.6.11.3 поставляется библиотека [RUNTIME].[STORAGE_MGR] содержащая процедуру init_temp_table для первичной инициализации временной таблицы. Данная процедура в качестве параметра принимает имя ТБП для которого создаётся временная таблицы. Например:

execute is
	v_cnt	integer;
begin
	[STORAGE_MGR].init_temp_table('LIST_DOMA');
	select x(count(1)) in ::[LIST_DOMA] into v_cnt;
       end;

Так как временная таблица создаётся внутри сессии БД, то бывает необходимость удержать сессию за пользователем и не возвращать в пул соединений до окончания работы с данными. Для этого необходимо установить в контексте USER_CONTEXT для переменной LOCK_SESSION значение = 1.
Таким образом, если sys_context(USER_CONTEXT, 'LOCK_SESSION') = 1 , то сессия не возвращается в пул и удерживается http-сессией, если http-сессий закрывается или в ней устанавливается sys_context(USER_CONTEXT, 'LOCK_SESSION') = 0, то сессия возвращается в пул.

Внимание! Следует помнить, что частое использование LOCK_SESSION может привести к увеличению количества активных сессий в БД и распуханию пула соединений.

Примеры использования на сессиюПоведение Для представлений с вычисляемыми колонками, для решения проблемы UDF. 
В операции фильтр функция отбирает экземпляры по некому условию.
Выполняем выборку, вставляем во временную таблицу, потом в представлении выводим В режимах 2MCA_Proxy, 2MCA, DBI операция-фильтр автоматически выполняется перед выборкой данных представления в той же сессии что и выборка данных, т.е. представление отработает корректно. В случае повторного выполнения представления (обновление, сортировка, фильтр, изменение количества выводимых строк) операция фильтр будет выполняться повторно в отличии от поведения в ТЯ1.

Выявление 
Непустое поле TEMP_TYPE в таблице CLASSES

Внимание!  Рекомендация по использованию индексов для временных таблиц. 
В PostgreSQL автоматический анализ временных таблиц никогда не производится. Если необходимо, чтобы для PostgreSQL индекс использовался, нужно выполнить команду сбора статистики по таблице после массового добавления/изменения данных. 
Для этого следует вызвать: ::[RUNTIME].[DB].get_temp_table_stat .  
Для Oracle процедура ничего не делает.

2.9. Количество выбираемых колонок в запросе
* Только для СУБД PostgreSQL

БД ограничивает количество колонок в запросе 1664. При превышении получим ошибку “…target lists can have at most 1664 entries…”

Получение такого большого количества колонок в запросе возможно например в случае оперирования экземпляром родительского ТБП с признаком “Может иметь экземпляры” (нет ключевого слова abstract в описании ТБП) у которого множество дочерних ТБП. В этот момент hibernate кэширует экземпляр с формированием запроса в БД , в котором объединяются таблицы родительского ТБП и всех его дочерних.

Решение следует искать на прикладном уровне, варианты зависят от конкретной причины ошибки:
* Сделать родительский ТБП абстрактным (abstract class …) 
* Сделать дочерние ТБП самостоятельными
* Убрать обращение к экземпляру родительского ТБП

3.2. Пустая строка и null
* Только для СУБД PostgreSQL

В PostgreSQL пустая строка ‘’ is not null. Это отличается от поведения в Oracle и СП runtime
Oracle

SQL> select case when '' is null then 'yes' else 'no' end from dual;

CAS
---
Yes

PostgreSQL
cft14=# select case when '' is null then 'yes' else 'no' end;
 case
------
 no

Это надо учитывать при написании кода запросов к БД. 

Код следует написать таким образом, чтоб не допускать появления ‘’ в текстовых полях БД ,т.к. существующий код в выборках проводит только анализ на NULL (is (not) null)

При использовании оператора || в SQL запросах следует явно приводить все слагаемые к строке, не допуская неявного приведения, т.к. для разных БД неявное приведение типов различается.


Выявление:

3.3. Execute immediate
* Только для СУБД PostgreSQL

Рекомендуется избегать прямого вызова в базу и использовать для этого соответствующие пакеты runtime.calc, runtime.plp и пр. В случае необходимости использования execute immediate требуется писать запрос таким образом, чтобы он мог одинаково проигрываться в разных средах, либо разделять через условия.

Например:
execute immediate 'truncate table Z#DBI_TEST'; Будет работать в Oracle но вызовет ошибку в PG так как имя таблицы не экранированно.
execute immediate 'truncate table "Z#DBI_TEST"'; Будет работать одинаково и в Oracle и PG.
execute immediate 'alter session enable parallel dml'; Не будет работать в PG, так как нет поддержки такого синтаксиса
execute immediate( 'begin :1:= some_function end;') using out v_test; Не будет работать в PG так как синтаксис анонимного блока отличается от синтаксиса Oracle

Внимание! При выполнении запросов посредством execute immediate к таблицам, следует иметь в виду, что платформа не обладает сведениями, куда будет произведен запрос. Поэтому, если ранее выполнялись вставки/обновления/удаления данных в этот ТБП, необходимо в прикладном коде принудительно сбрасывать кэш в БД командой cache_mgr.cache_flush().

Выявление:
Через плагин PLPCheck , проверки EXECUTEIMMEDIATE, OBLIGATORY_UNIQUE_ALIAS

3.5. When others 
* Только для СУБД PostgreSQL

PostgreSQL в отличие от Oracle «портит» транзакцию при возникновении исключений большинства групп. О группах см. подробнее тут https://www.postgresql.org/docs/12/errcodes-appendix.html . После возникновения таких ошибок попытка выполнения любой команды SQL/DML будет сопровождаться исключением группы 25 – Invalid Transaction state, например, 
25P02 - ERROR: current transaction is aborted, commands ignored until end of transaction block. 
На текущий момент конструкция when others перехватывает исключения всех групп. Поэтому без правильной обработки исключений что-либо получить/положить в базу не удастся. Нужно обязательно делать либо rollback минимум до точки исполнения проблемного запроса, либо выбрасывать исключение наружу – raise/error, но ТОЛЬКО если в блоке кода могут произойти исключение в БД. 

Также правила обработки исключений приведены в пункте 3.18.

Выявление:
любой блок exception when others без генерации исключения или rollback

3.6.2. Сериализация
На СП в результате сериализации в тексте xml может появиться декларация (которой в Платформе 1 не было). Если эта декларация является нежелательной (определяется спецификой приложения), её можно удалить вызовом процедуры RUNTIME.XML_DB.set_xml_encoding(v_xml_clob, null).

Не препятствует адаптации кода на DBI. 

3.6.3. Кодировки в XML
На СП в некоторых случаях учитывается кодировка, указанная в декларации xml. Это может приводить к ошибкам при парсинге или неверной кодировке в результате. Ожидаются доработки ТЯ, которые будут игнорировать декларированную кодировку, требуя, при этом, соответствия текста xml кодировке среды исполнения (БД или СП).
Для минимизации проблем, связанных с кодировкой текста в xml следует выполнять следующие правила:
* Обрабатывать следует только xml, текст которого соответствует кодировке среды исполнения.
Если текст xml получен из внешнего источника (например, файла) или хранится в бинарном виде (blob), то требуется самостоятельно привести его к кодировке среды исполнения функциями библиотеки RUNTIME.CHARSET. Для получения кодировки среды исполнения следует использовать функцию RUNTIME.CHARSET.default_charset.
* На СП перед парсингом xml функциями библиотек XML_DB и XML_DOM, при выполнении пунктов (1) и (2), следует удалять декларацию процедурой RUNTIME.XML_DB.set_xml_encoding(v_xml_clob, null).
(1) Предполагается последующее редактирование xml и/или сериализация;
(2) Есть вероятность, что в xml есть декларация с атрибутом encoding, в котором указана кодировка отличная от «ISO-8859-5».
Внимание! Ожидается доработка со стороны ТЯ, в результате которой кодировка декларации будет игнорироваться, а будет использоваться кодировка среды исполнения.
* При передаче xml во внешнюю систему (или выгрузке в файл), если требуется конкретная кодировка в декларации, её следует обеспечить вызовом процедуры RUNTIME.XML_DB.set_xml_encoding(v_xml_clob, 'UTF-8'). Если данные передаются в бинарном виде, то также следует обеспечить перекодирование текста в требуемую кодировку функцией библиотеки RUNTIME.CHARSET (например, clob_to_blob).
* На СП, при использовании xsl-трансформации через метод xmltype.transform, требуется обеспечить кодировку СП (которую можно получить функцией RUNTIME.CHARSET.app_srv_charset):
o В декларациях xml-документа и xsl-шаблона;
o В атрибуте encoding инструкции xsl:output.
Внимание! Ожидается доработка со стороны ТЯ, в результате которой все вышеупомянутые кодировки будут игнорироваться, а везде будет использоваться кодировка среды исполнения.


Выявление:
Проверка по текстам исходного кода на PlPlus с последующим анализом разработчиком.

3.8. Триггеры 
Триггеры базы данных относятся к серверному коду и возможны к использованию только для Платформы 1 и Платформы 2МСА. 
Для архитектуры DBI есть возможность использовать операции типа Триггер, но они не совместимы с Платформой 1. 
Рекомендуется для платформы DBI продублировать реализацию триггеров через операции и при миграции отключить триггеры в БД. Так же возможно создание триггеров напрямую в БД, но, в виду отсутствия пакетов в БД, функционал таких триггеров может быть ограничен.

Если требуется обеспечить одновременную работу с СУБД Oracle в различных архитектурах (Платформа 1, 2MCA, DBI), в триггерах БД, функционал которых продублирован в операции типа "Триггер",  необходимо добавить в начало триггера следующий программный код:
if not attribute_mapping_service.is_enabled then return; end if;
При этом, на СП в файле settings.xml должна быть включена настройка:
<entry key="enable-attribute-mapping-service">true</entry>
Это приведёт к тому, что программный код триггера БД не будет выполняться, если сессия 3L.

Внимание! Операция триггер не будет выполняться, если DML команда будет выполнена посредством execute immediate, rtl.execute_sql и т.п.  Связано это с тем, что перехват CRUD кода для вызова операции триггера осуществляется средствами hibernate и любой программный код выполняющийся в обход hibernate, им перехвачен не будет. Категорически не рекомендуется создавать код, который модифицирует данные в обход hibernate в ТБП, в котором есть операция триггер.

Внимание! В режиме DBI на Oracle в триггерах БД запрещено вызывать интерфейсы ТБП, операций и других платформенных пакетов. Связано это с тем, что при таком вызове будет произведена “тяжелая” инициализация сессии и она начнет считаться 2L сессией.

3.11. Ограничения типизации
      DBI приложение более чувствительно к приведению типов.
* При определении переменных как %rowtype от таблицы или представления в разных операциях, это будут разные типы. Аналогично с объявлением курсоров.
Пример:
       library LIB is
       public function test2 return dual%rowtype is
       v_test dual%rowtype;
       begin
		…
       end;

       method RUN1 is
       execute is
       par1	dual%rowtype;
       begin
		par1 := [LIB].test2;
end;

Данный код приведёт к ошибке компиляции The method assign(RUN1.DUAL_$ROWTYPE) in the type RUN1.DUAL_$ROWTYPE is not applicable for the arguments (LIB.DUAL_$ROWTYPE)

* Если параметр функции определён как массив ссылок на определённый тип, то в него нельзя передавать массив number или reference. 
Пример:
       public type testTableType is table of ref [DBITEST];

       public procedure test1(par1 testTableType) is
       begin
		…
       end;

       public procedure run1 is
       par1	constant.REFERENCE_TABLE;
       begin
		test1(par1);
       end;
Данный код приведёт к ошибке компиляции The method TEST1(Dbitest.Ref.Table) in the type LIB is not applicable for the arguments (Dbitest.Ref)

3.12. Регулярные выражения
Необходимо учитывать различия при работе с регулярными выражениями в Java, Oracle и PostgreSQL, и тестировать функции с конкретными регулярными выражениями в каждой возможной среде выполнения:
* «Платформа 1»  – функция всегда выполняется в СУБД Oracle.
* 2MCA (DBI)  – функция выполняется:
o в СУБД Oracle или PostgreSQL, если она используется в команде SQL.
o в Java, если она используется в выражении PL+.
В PostgreSQL для «ЦФТ Банк» будут использоваться хранимые функции-обёртки (regexp_replace, regexp_substr, regexp_instr, regexp_count, regexp_like), которые по набору параметров идентичны функциям Oracle. Для них поддержаны те же флаги, что и в Oracle (выполняется замена флагов Oracle на флаги PG), и по умолчанию будет использоваться флаг "p" (см. документацию PostgreSQL), если явно не был указан флаг "m" (многострочный текст). Флаг "p" для PG выбран, как обеспечивающий более похожее поведение с Oracle. По умолчанию, при использовании оригинальных функций, в PG используется флаг "s", поведение которого отличается и от Oracle, и от Java.
Ниже перечислены различия, о которых известно на текущий момент. Список будет пополняться по мере выявления новых различий.
1. Различие в обработке символов \r (возврат каретки, код - 13) и \n (новая строка, код - 10)

Совпадение с шаблоном "."
(любой символ)Совпадение с шаблонами отрицания
\D, \W и шаблоны типа [^ABC]\r\n\r\nOracleДаНетДаДаPostgreSQLДаНетДаНет2MCA (Java)НетНетДаДа
Примеры:
replace( replace (
      regexp_replace('a'||chr(13)||chr(10)||'b', '(.)', '<\1>')
, chr(13), '\r'), chr(10), '\n')Oracle<a><\r>\n<b> PostgreSQL<a><\r>\n<b> 2MCA (Java)<a>\r\n<b> 
replace( replace (
      regexp_replace('12'||chr(13)||chr(10)||'34', '(\D)', '<\1>')
, chr(13), '\r'), chr(10), '\n')Oracle12<\r><\n>34 PostgreSQL12<\r>\n34 2MCA (Java)12<\r><\n>34 
2. Ошибки для некорректных или неподдерживаемых регулярных выражений
2.1. Указан несуществующий номер группы, при повторном поиске ранее найденных групп символов.
Пример: regexp_replace('ZabcxyzabcZ','(abc)xyz\2','#')
В Oracle и PG – ошибка "недопустимая обратная ссылка". В Java – нет ошибки.
2.2. Квантификатор после ^ и $ ("^*", "^+", "^?", "$*", "$+", "$?")
Примеры:
* regexp_replace('abc','^*','x'), regexp_replace('abc','^+','x')
* regexp_replace('abc','$+','x'), regexp_replace('abc','$?','x')
В Oracle и Java – нет ошибки (^ и $ совпадают с началом и концом строки).
В PG – ошибка "quantifier operand invalid".
2.3. Сверхжадная (ревнивая) квантификация
Пример: regexp_replace('abcccccc', '(ab)(c*+)(c)', '[\1]<\2>[\3]')
Результат в Java: " abcccccc" – замены нет (совпадение не найдено), что означает, что ревнивая квантификация работает, запрещая возвращаться к предыдущим шагам (в данном случае, чтобы захватить последний символ "c", как было бы для жадной квантификации).
В Oracle результат "[ab]<ccccc>[c]" – такой же, как и для жадной квантификации, т.е. ошибки нет, но ревнивая квантификация не работает.
В PG – ошибка " quantifier operand invalid".

3. Поиск группы с пустым шаблоном ()* по номеру в функции regexp_instr
Пример: regexp_instr('abc def','()*def',1,1,0,'',1)
В Oracle и PG – результат 5. В Java – 0.
При этом, результат функции regexp_replace('abc def','()*(def)','[\1]<\2>') везде одинаков – "abc []<def>", т.е. здесь Java всё-таки видит этот пустой шаблон.

4. Различия в функции regexp_replace при экранировании символов в строке замены
Пример: regexp_replace('12345-text', '^(\d{5}).*', '\1\xyz') 
Результат в Oracle и PG – "12345\xyz". В Java – "12345xyz".
Пример: regexp_replace('12345-text', '^(\d{5}).*', '\1\\xyz') 
Результат везде одинаков – "12345\xyz".

5. Использование метасимволов (\d, \s и др.) в наборах символов
Oracle не воспринимает \d и \s в наборе символов как метасимволы, а считает их обычными символами "s", "d" и "\". PG и Java интерпретируют \d и \s как метасимволы (цифры и пробельные символы).
Пример: 
regexp_replace('sd\12  34\ds','([\s\d]+)', '<\1>')Oracle<sd\>12  34<\ds> PostgreSQLsd\<12  34>\ds 2MCA (Java)sd\<12  34>\ds
Функции будут поставляться в рамках Обновления ЦФТ-Банк.  Ознакомиться можно тут https://bs-gitlab-pub.ftc.ru/oae-app/dbi/pg_standard_funcs

3.14. Прочие ошибки в JAVA коде

Выявление по всем пунктам: Проверка ошибок компиляции в JAVA.

3.14.1. Unreachable code
Данная ошибка возникает, когда компилятор считает, что данный код никогда не может быть выполнен. Чаще всего это бывает связано либо с попытками обойти некий вызываемый блок, либо транслятор может ошибаться.

Пример:
public function setCharSet(p_clob CLOB) return CLOB is
begin
	return p_clob;
pragma IF_DEF (EXCEPT);
exception when others then
	pragma error ('test');
pragma END_IF;	
end;
   
	

3.14.2. The code of method % is exceeding the 65535 bytes limit
Согласно спецификации JAVA есть ограничения на размер методов. Требуется сократить размер прикладного кода

3.14.3. % cannot be resolved to a type
Данная ошибка возникает, если сгенерированный JAVA код ссылается на несуществующий пакет. Возникает в случаях, если при компиляции у вызываемой операции не получилось сгенерировать JAVA код, либо стоит «не компилировать в java», либо пакет не имеет java реализации, например : partiotion_mgr.

3.14.4. % is not applicable for the arguments %
Данная ошибка возникает при отсутствии в JAVA реализации метода с необходимым набором параметров. Наиболее часто к этой ошибке приводят ошибки типизации. Список параметров находится в сообщении об ошибке, необходимо его проанализировать.

Исключением является сообщение вида: 
The method getPackage(Class<T>) in the type Context is not applicable for the arguments (Class< … >) , которое говорит об отсутствии класса и схоже с предыдущим пунктом.

3.14.5. % is undefined for the type 
Данная ошибка появляется при отсутствии необходимого метода внутри пакета, что наиболее часто вызвано отсутствием java реализации. Необходимо избавляться от их использования.

Частным случаем является ошибка:
The method getValue() is undefined for the type %.Ref
Такая ошибка может встречаться при попытке выборки из ссылки, например:
v_md	ref	[MAIN_DOCUM];
begin
	for ( select x(count(1) : C_COUNT) in v_md ) loop
		null;	
	end loop;
end; 

3.14.6. Duplicate method JSON_OBJECT_T() in type WEB_REP.JSON_OBJECT_T_$OBJECT 
Ошибка возникает при попытке обращаться к объектным типам нереализованным в 2MCA DBI. Например: JSON, AQ$_JMS_MAP_MESSAGE. 
В случае с JSON рекомендуется использовать реализацию LIB_JSON из RUNTIME.

3.14.7. Duplicate method
Ошибка возникает при появлении в JAVA коде одинаковых описаний методов. Наиболее частая причина - наличие одноимённых функций или процедур с одинаковым набором обязательных параметров. В отличии от Oracle ошибка будет на этапе компиляции, а не на этапе вызова. Например:

public function test1(p1 varchar2(4000)) return number is
begin
	null;
end;

public function test1(p1 varchar2(4000),p2 number := 0) return number is
begin
	null;
end;

3.14.8. Duplicate local variable
Данная ошибка говорит о повторном объявлении переменной в JAVA. Необходимо проанализировать код и найти источники объявлений. Причиной может быть разный уровень видимости переменных. Пример, неработающий в JAVA:
type main is select x('1') in dual%rowtype;

type arr_main_data is table of main%rowtype;
aMainData			arr_main_data;

begin
	for curData in cursor main
	loop
		null;
	end loop;

	var curData main%rowtype;
	curData := aMainData(1);
end;

3.14.9. Cannot cast
Ошибка приведения типов. Oracle допускал что типы одинаковые, если результаты их выборок совпадают. В JAVA требования более строгие. Подробно ограничения описаны в п.3.11

3.14.10. Экземпляр был изменен или удален другой транзакцией
Ошибка возникает когда другая сессия изменила экземпляр, пока с ним работала наша сессия. Подробно механизм описан в п.6.5 “Сброс кэша”. 
Способ исправления – предварительно проверять экземпляр на блокировку, и, если он не заблокирован, блокировать и производить дальнейшую обработку.

3.16.1. Библиотека для работы с кодировками
Для унификации работы с кодировками символов в версии "ЦФТ Банк" 22.4 создана библиотека ::[RUNTIME].[CHARSET], содержащая функции, поддерживаемые в DBI. Библиотека, в частности, содержит функции для перекодирования данных типов varchar2, raw, clob, blob.

3.16.2. Коды символов и символы
В разных кодировках коды символов могут различаться. Коды символов, которые использовались до сих пор, соответствуют кодировке CL8ISO8859P5 (ISO-8859-5), так как для БД Oracle этого требует Платформа ЦФТ. Для БД PostgreSQL Платформа ЦФТ будет требовать кодировки UTF8 (UTF-8). Таким образом, коды, которые сейчас используются в программном коде как константы, могут означать разные символы при работе с разными БД, что может привести к некорректным результатам. В связи с этим, вводятся следующие требования к программному коду:

3.16.2.1. Диапазон кодов символов, идентичных в разных кодировках
Символы с кодами 0..127 одинаковы для всех кодировок, поэтому их допускается использовать в программном коде (как SQL, так и PL+) без изменений.

3.16.2.2. Функции для работы с кодами и символами в процедурном коде
Для получения кода символа или символа по коду для требуемой кодировки следует использовать функции ::[RUNTIME].[CHARSET].ascii и ::[RUNTIME].[CHARSET].chr. Эти функции следует использовать только в PL+

3.16.2.3. Функции для работы с кодами и символами в SQL
При необходимости использования в командах SQL функций ascii и chr для кодов, которые больше 127, следует до выполнения команды SQL получить код символа в БД (или символ по коду в БД) функцией из библиотеки ::[RUNTIME].[CHARSET], указав кодировку БД (см. функцию db_charset), и использовать результат в команде SQL

3.16.3. Кодировка среды исполнения

3.18. Ограничение при работе с транзакциями
      
3.18.1. Прерванные транзакции
* Только для СУБД PostgreSQL

При возникновении большинства ошибок в PostgreSQL транзакция считается прерванной. Для продолжения работы в БД есть два варианта:
1. Зафиксировать транзакцию.
2. Откатить транзакцию на точку отката, установленную до возникновения ошибки.
Если этого не сделать то после возникновения исключения при выполнении любой команды SQL/DML вернётся ошибка «25P02 - ERROR: current transaction is aborted, commands ignored until end of transaction block».

Для информации: группы исключений PostgeSQL - https://www.postgresql.org/docs/12/errcodes-appendix.html .

Без правильной обработки исключений БД в процедурном коде выполнить команду SQL/DML в БД после перехвата исключения не удастся. В процедурном коде нужно обязательно:
* либо делать rollback минимум до точки исполнения проблемного запроса, 
* либо генерировать raise/pragma error (для которых приложение само делает откат), 
* либо фиксировать транзакцию.

Для каждого варианта есть свои причины, особенности и ограничения.

Важно понимать, что:
1. Проблема актуальна для исключений, генерируемых из БД. 
Исключения, генерируемые процедурным кодом, не требуют дополнительной обработки. Например, NO_DATA_FOUND, TOO_MANY_ROWS, OBJECT_NOT_FOUND (даже в динамическом SQL), а также прикладные исключения.
2. При генерации исключения после перехвата не стоит его подменять другим исключением, которое не относится к группе исключений БД без предварительного отката транзакции, иначе невозможно будет его правильно обработать выше по стеку, так как оно не будет восприниматься как исключение БД.
3. Исключения БД, генерируемые при вставке/обновлении/удалении данных будут генерироваться при сбросе кэша СП (hibernate) в БД, а это не всегда именно место перехвата исключения. В данном случае необходимо использовать инструменты управления кэшем, например, принудительный сброс кэша в БД для явной генерации исключения в БД и дальнейшего перехвата. Особенности работы Hibernate изложены в видео (\\pumba\bft\ РАБОЧИЕ ДОКУМЕНТЫ\Учебные материалы\DBI\2023 Особенности работы Сервера приложений. Hibernate. КоплиВ-20230203_140256-Запись собрания.mp4). Текстовое описание будет приведено позже.   
4. Исключения внутри динамического SQL - всегда исключения БД. Кроме вышеописанных исключений.
5. См. п. 3.18.2



Примеры исключений внутри БД:

* Ошибки исполнения, например, деление на ноль
test=# BEGIN;
BEGIN
test=*# select 100/0 from dual;
ОШИБКА:  деление на ноль
test=!# select * from dual;
ОШИБКА:  текущая транзакция прервана, команды до конца блока транзакции игнорируются

* В среде разработки так же возможны ошибки, связанные с ошибками синтаксиса. Ожидается, что в промышленной среде такие ошибки не должны возникать.
test=# BEGIN;

test=!# select * from dual;
ОШИБКА:  текущая транзакция прервана, команды до конца блока транзакции игнорируются

3.18.2.  Ограничение на количество подтранзакций. Установка savepoint.
* Только для СУБД PostgreSQL

В БД PostgreSQL есть ограничение на количество создаваемых подтранзакций внутри одной транзакции, связанное с деградацией производительности. Каждая точка отката порождает одну подтранзакцию. Настоятельно не рекомендуется допускать превышение 64 подтранзакций. Надо не забывать, что технологическое ядро так же может ставить точки отката, например: при запуске секции EXECUTE, выполнении валидации и т.д. 

Не рекомендуется устанавливать savepoint при обработке каждого экземпляра при массовых обработках экземпляров, в таком случае количество подтранзаций будет зависеть от количества обрабатываемых экземпляров. Рекомендуется в таких случаях разделять обработку на группы, количество которых не превышает 64 и фиксировать/откатывать транзакции группами.

Внимание, в случае, если количество транзакций превышает 64, то возможно возникновение деградации производительность БД, что может привести к отказу в обслуживании.

Выявление:
* Анализ блоков кода с перехватом исключений на наличие там откатов к точкам сохранения
* При исполнении кода, т.е. на этапе тестирования в высококонкурентной среде  

Внимание! Не препятствует адаптации кода на DBI на Oracle.

В версии СП 3.11.33, ТЯ 7.7.1.9  появилась возможность удалить savepoint командой cache_mgr.cache_release. В PostgreSQL команда выполнит release savepoint. Для Oracle команда не будет ничего делать. 

Рекомендуется удалять savepoint при массовом использовании savepoint c одним и тем же именем, например при работе в цикле. Информация по использованию команды находится в документации CFT Platform IDE -> раздел "Приложение 3. Описание PL/Plus > Описание языка PL/Plus > Управление транзакциями". 

Внимание! Удаление savepoint не уменьшит количество субтранзакций, но существенно ускорит работу PostgreSQL по поиску родительского savepoint в случае выполнения rollback, а также освободит часть ресурсов БД.

3.18.3. Признак “Операция контролирует транзакцию”

Не рекомендуется к использованию свойство операции “Операция контролирует транзакцию” (задается на вкладке Properties в редакторе экранной формы). При запуске такой операции, транзакция удерживается на все время ее работы. Таким образом удерживается горизонт транзакций, что негативно сказывается на работе всей системы. Более подробно о горизонте написано в п.5.3

Выявление:
Через плагин PLPCheck , проверка с кодом FORM_TRANSACT_CONTROL

3.18.4. Размерность имен savepoint, rollback

Если используются макросы &sp и &rb библиотеки ::[RUNTIME].[MACRO_LIB], то на имя остается и того меньше, 28 символов, т.к. идентификатор операции для NativeID равен 35 символам.

3.21. Условная компиляция
Все разновидности условной компиляции запрещены и не имеют смысла в DBI, т.к. программный код поставляется в уже в скомпилированном виде

* ::[RUNTIME].[PLP]
* ::[RUNTIME].[PLP2]  - только  для java
* Справочник “Расширения и перекрытия. Точки вызова” (APPAUX_CALLPOINT)
* Макрос substitude
* Использование статичного кода

Через плагин PLPCheck

3.23. Конкатенация CLOB/BLOB/varchar2

Если в коде многократно выполняется dbms_lob.write, dbms_lob.writeappend, dbms_lob.append для CLOB/BLOB, либо многократно выполняется конкатенация ||,concat для varchar2, рекомендуется использовать специальную библиотеку конкатенации ::[RUNTIME].[CONCAT_LIB]. Она позволяет существенно увеличить быстродействие и снизить нагрузку на СП в DBI .

3.24. Обобщенные ссылки в представлении

В PostgreSQL нет аналога представления OBJECTS как в Oracle, через, которое можно было бы от ID получить CLASS_ID. Поэтому при создании колонки с автоматическим переходом в "Обобщенную ссылку"(REFERENCE) переход не будет работать. Для того, чтобы переписать такие переходы, необходимо вычислить CLASS_ID самостоятельно, через любые легитимные способы (например, хранить класс в новой колонке) и конкатенировать это значение к идентификатору с разделителем в виде двоеточия. Т.е. итоговое значение должно выглядеть примерно так: MAIN_DOCUM:123456789. 

Выявление:
Через плагин PLPCheck , проверка с кодом REFERENCED_TO_OBJECT


3.25. Различная реализация запросов для Oracle/PostgreSQL в представлении

В некоторых случаях в представлении может потребоваться выполнить для колонки(ок) различную обработку запроса для БД Oracle  и PostgreSQL. Для этого следует воспользоваться системной переменной условной компиляции COMPILE$TARGET, которая может принимать значения ‘DBI.ORA’ и ‘DBI.PGS’. Пример использования

class MAIN_55446;

@name('Представление с условной компиляцией')
view VW_CRIT_MAIN_55446 {
    type main is
        select a(a.[R_STR] : C_R_STR1, 
--#if &COMPILE$TARGET = 'DBI.PGS'
		(select b(b.[R1]) in ::[TARGET_55446] all where b = a.[R_REF]) : ref1,
--#else
       	a.[R_REF].[R1] : C_R_REF#R1 ,
--#endif
        	::[MAIN_55446].[LIB].test_func(a.[R_REF]) : f1,
        	a.[R_STR] : C_R_STR2 
        )
        in ::[MAIN_55446];
    
}

4.4.1. Интегратор. Синхронное взаимодействие
В связи с ограничениями пунктов 4.2 и 4.3, в Интеграторе станет невозможным синхронное взаимодействие с другим Интегратором (в т.ч. в одной транзакции). Выявление:

Следует иметь в виду, что это настраиваемое значение, которое банк может изменять самостоятельно, поэтому, дополнительно, для каждого обмена следует проанализировать рекомендации по настройкам бизнес-процесса в документации прикладного приложения.

Вызовы обработчиков Интегратора из внешней системы подпадают под пункт 4.3. Но здесь для выявления можно использовать дополнительный косвенный признак: наличие прямых привилегий, выданных пользователям на пакет библиотеки CIT_BO.EXT_CALL_LIB. Если кому-то была выдана такая привилегия, то с большой вероятностью это было сделано для внешнего вызова под этим пользователем.

where p.PRIVILEGE = 'EXECUTE' and p.TABLE_NAME = 'Z$CIT_BO_EXT_CALL_LIB'
Рекомендации по выполнению требования те же, что в п. 4.2. и 4.3. соответственно.

4.4.3. Интегратор. Управление очередями
Для управления очередями используется библиотека RUNTIME.AQ_LIB, которая прозрачно для приложений использует брокер сообщений, настроенный на общесистемном уровне.
В архитектуре DBI, если СУБД – Oracle, можно продолжать использовать Oracle AQ (рекомендуется, так как при этом сохраняется та же функциональность, что и в Платформе 1), или можно переключиться на использование брокера сообщений Apache ActiveMQ.
Если СУБД – PostgreSQL, то использование Apache ActiveMQ является обязательным.
Подробное описание настроек СП и Apache ActiveMQ, требуемых для ЦФТ-Банк, а также ограничения (отличия от Oracle AQ), см. в "Документация по подсистемам" / ШЛЮЗЫ / IBSO_2MCAQueuing.
В частности, при использовании ActiveMQ:
* Интегратор не управляет пропагацией (в т.ч. выполняемую через Oracle MGW). Если требуется пропагация, то её следует настраивать на стороне ActiveMQ.
* Теряют смысл операции «Назначить администратора подсистемы», «Исключить пользователя из администраторов подсистемы», а также выдача пользователю прав на работу с очередями (в операции «Управление окружением»), которые предназначены только для управления очередями Oracle AQ.
Исправлений кода не требуется.

4.4.4. Интегратор. Транзакционность при получении сообщений
Следует иметь в виду, что в СУБД и брокере сообщений Apache ActiveMQ, управление транзакциями выполняется раздельно. Поэтому, отсутствует гарантия, что
* изменения в БД зафиксируются синхронно с помещением сообщения в очередь (транзакционность помещения в очередь настраивается в бизнес-процессе)
* извлечение сообщения из очереди сможет успешно зафиксироваться после завершения фиксации транзакции в БД (транзакционность получения из очереди управляется настройкой "CIT_DEQUEUE_VISIBLE_ON_COMMIT")
Такие проблемы могут произойти, например, в результате аппаратного сбоя.


5. Оптимизация
5.1. Точечные запросы. 
Массовые уникальные точечные запросы могут серьезно снизить производительность кода, т.к. помимо непосредственного времени выполнения каждого запроса, к нему добавляется время сетевого взаимодействия.  

Примеры подобного кода :
Разыменование ссылочных реквизитов в курсоре (проверка в PLPCheck suboptimal_unselected_col_usage )


    for (select i(i.[ACC_CORR] : ACC_CORR) in ::[RECORDS] where i%collection = a and i.[DOC] = c) loop
        d := i.[ACC_CORR].[MAIN_V_ID];
    end loop;
      Пример исправления:
	for (select i(i.[ACC_CORR].[MAIN_V_ID] : MAIN_V_ID) in ::[RECORDS] where i%collection = a and i.[DOC] = c) loop
        d := i.[MAIN_V_ID];
    end loop;

Примечание: 
Не всегда точечный запрос будет понижать производительность:
* Если ТБП, реквизиты которого разыменовываются по ссылке, помещен в кэш второго уровня hibernate, то при первом обращении, экземпляр будет закэширован и далее будет обращение только к кэшу (см. раздел 6) 
* Запрос может быть помещен в кэш 1 уровня, который может содержать до 200 кэшируемых экземпляров (см. раздел 6)
* Если выборка содержит небольшое количество экземпляров, то точечный запрос может оказаться быстрее, чем выполнение соединения таблиц.
В каждом случае надо принимать решение используя результаты анализа производительности:  время выполнения исследуемого блока кода, топ запросов по количеству, по времени выполнения и т.д.,  и на основе пунктов данного примечания.

Более подробно кэширование рассмотрено в Разделе 6 данного документа.

5.2. Varray, как альтернатива временным таблицам (temp table).  Ограничение размера массива
Хорошей альтернативой использованию временных таблиц могут служить varray. Следует только учитывать, что их использование будет потреблять память СП, а также оказывать влияние на сетевой трафик БД-СП. Поэтому в программном решении нужно заранее оценивать возможные размеры массива. С множеством оговорок (количество и размер колонок, типы данных и т.д.) максимальной границей можно считать 10 тысяч записей.

Для массивов типа table of ограничение в 10 тысяч записей также актуально

5.3. Длительные транзакции, горизонт.
* Только для СУБД PostgreSQL

Сочетание архитектуры СУБД PostgreSQL и jdbc драйвера таково, что незавершенная транзакция (не каждая и не полностью, подробности ниже) начинает оказывать замедляющее воздействие на работу всей БД. 
Эффект тем сильнее, чем длительнее транзакция и большее количество транзакций началось после нее.

Ощутимый замедляющий эффект наблюдается, когда количество транзакций, начавшихся после незавершенной, достигает 7млн. 15 млн – уже красная зона для БД. Цифры не абсолютные, зависят от конфигурации БД, особенностей эксплуатации и других факторов, но позволяют понять приблизительные границы.
Статистика динамики транзакций такова: 
* Средний региональный банк – 7млн. транзакций за сутки.
* Крупный банк - 7млн. транзакций достигается за час работы.

Поэтому возникает несколько требований и рекомендаций к написанию кода.
1. длительность транзакции не должна превышать 20 минут
2. нужно избегать генерации множества транзакций в короткий промежуток времени. Оценочные цифры – при работе алгоритма не превышать более 10 транзакций в секунду.

Более подробно:

1. Длительные транзакции
До завершения длительной транзакции (не каждой и не полностью, подробности ниже) автовакуум не сможет удалить устаревшие версии строк, у которых идентификатор транзакции более новый, чем у длительной. Это приводит к раздуванию таблиц.  Начинает расти так называемый горизонт – количество транзакций между началом выполнения длительной и всеми транзакциями, начавшихся после длительной. PostgreSQL вынужден при каждом запросе к данным проводить анализ и отсеивать устаревшие версии строк. Это приводит к деградации производительности.

Говорим только о следующих незавершенных транзакциях, которые влияют на производительность БД :
* в которой произошло изменение данных в БД, начиная с момента изменения. Т.е. если транзакция длится час, но изменение было только на 50 минуте, то отсчет начинается с 50-ой минуты и горизонт будет удерживаться 10 минут.


* в которой есть читающая активность (select ) c момента начала запроса и до начала следующего запроса. Т.е. если запрос длится 60 минут, и следующий начнется через 5 минут по окончанию первого, что то отсчет будет  с 1 и до 65 минуты, т.е. горизонт будет удержан 65 минут.



Оценивать время следует исходя из своего опыта и знания продукта/подсистемы. Сейчас разрабатываются механизм, который позволит выявлять операции, представления с максимальными временами транзакций на комплексах, в т.ч. в банках. На время будет оказывать влияние особенности данных конкретного банка, планируемая нагрузки на БД. Способы уменьшения времени транзакции зависят от алгоритма и бизнес процесса. Это может быть разбитие обрабатываемых данных на логические порции и ввод промежуточных состояний. Может быть фиксация промежуточных результатов. Может быть оптимизация алгоритма. Для пишущих транзакций следует как можно позже совершать update/delete, тем самым будет отодвигаться начало удержание горизонта. 

2. Количество транзакций
Следует принимать по внимание, что счетчик транзакций увеличивается и в случае субтранзакций, т.е. в случае каждого savepoint. Само по себе количество транзакций не является чем-то критичным. Но эффект появляется при наличии длительных транзакций.
Требование по длине транзакции с одновременным ограничением их количества в единицу времени заставляет искать компромисс между этими требованиями.  Опять же способы уменьшения количества транзакций зависят от алгоритма и бизнес процесса. Не следует злоупотреблять частыми savepoint и commit.


6. Кэширование в платформе 2MCA/2MCA DBI

6.1. Термины

ORM - Object-relational mapping. Слой для связи объектов БД и сущностями в java. Представляет собой автогенерируемые java классы на основе описания ТБП. В данном документе считаем 1 ТБП = 1 ORM класс.
ORM объект – экземпляр java класса, т.е. это потенциальный или существующий экземпляр ТБП.
Hibernate – фреймворк, реализующий ORM.
Кэш hibernate – кэш экземпляров БД. Строго говоря сам hibernate не кэширует. Реализацию кэширование выполняет отдельное ПО, в нашем случае это EHCache
Кэш 1 уровня – это кэш сессии hibernate. Обратите внимание, что имеется ввиду сессия hibernate,  это не сессия БД и не прикладная сессия.
Кэш 2 уровня – это межсессионный кэш hibernate. Т.е. кэш уровня СП в отношении каждой БД, на которые настроен СП.


6.2. Роль hibernate в платформе

Платформа 2MCA/2MCA DBI использует hibernate, как одно из средств доступа и взаимодействия с объектами БД. Другим средством взаимодействия является выполнение прямых SQL запросов.

Работая с ссылками в PL+ коде, в java происходит обращение к ORM объектам. При этом, в соответствии с алгоритмами, описанными ниже, происходит или обращение только к кэшу или также производится обращение к БД. 
Для написания производительного кода в архитектуре 2MCA/2MCA DBI, следует понимать, как и когда работает кэш hibernate.

6.3. Алгоритм кэширования

* Вариант 1. ТБП не включен в кэш второго уровня (как включить – ниже, в более подробном описании кэша 2 уровня). Когда идет обращение к полям ORM объекта (кроме ID), всегда и безусловно проверяется его наличие в кэше первого уровня. Если объект не найден, hibernate выполнит точечный запрос к базе данных, полученные данные будут помещены в кэш первого уровня и возвращены пользователю.
* Вариант 2. ТБП включен в кэш второго уровня (как включить – ниже, в более подробном описании кэша 2 уровня). Когда идет обращение к полям ORM объекта (кроме ID), всегда и безусловно проверяется его наличие в кэше первого уровня. Если объект не найден, hibernate проверяет кэш второго уровня (межсессионный кэш). Если объект найден в кэше второго уровня, он будет загружен в кэш первого уровня и возвращен пользователю. Если объект отсутствует и в кэше второго уровня, hibernate выполнит точечный запрос к базе данных, а полученные данные будут сохранены в обоих уровнях кэширования.

Когда выполняется команда сохранения или обновления в БД ORM объекта, его состояние также автоматически обновляется в кэше второго уровня.

Когда выполняется команда удаления ORM объекта, он также удаляется из кэша второго уровня. 

Следует отметить, что кэширование на прикладном уровне никак не связано с данным механизмом. Прикладной кэш, полезный в режиме ТЯ1, может быть бессмысленным или даже замедлять работу в режиме 2MCA/2MCA DBI, т.к. будет дополнительно оказывать нагрузку на систему.


6.4. Функции управления кэшем, доступные из PL+

* cache_mgr.cache_clear() - удаление экземпляров всех ТБП из кэша.
* cache_mgr.cache_refresh(ref ТБП) – обновление в кэше указанного экземпляра
* cache_mgr.cache_refresh_class(короткое имя ТБП) - обновление в кэше экземпляров указанного ТБП 
* cache_mgr.cache_flush() -- сброс экземпляров всех ТБП в БД. Кэш не обновляется.
* cache_mgr.cache_flush(ref ТБП) – не использовать, deprecated. Перевызов cache_mgr.cache_flush()

6.5. Сброс кэша

Сброс кэша, другими словами сохранение кэша в БД, осуществляется при:
* завершении выполнения операции либо задания по расписанию
* commit/savepoint/rollback
* выполнении прикладным кодом запросов в БД в обход hibernate (select/update/delete). Производится сброс кэша для всех таблиц, участвующих в запросе.
* перед выполнением операции триггера
* вызове cache_mgr.cache_flush 

Перед выполнением сброса кэша для изменяемых экземпляров выполняется select for update без ожидания для получения блокировки. При невозможности блокировки, платформа сгенерирует исключение.
В  таблице и ORM соответствующим каждому ТБП, есть атрибут, который хранит номер версии изменения экземпляра – SN. При кэшировании экземпляра, запоминается SN. В дальнейшем, если объект изменялся и выполняется процедура сброс кэша в БД, инструкция UPDATE содержит дополнительное условие, которое проверяет, равен ли закэшированный SN значению в БД. Если не равен, платформа сгенерирует исключение “Экземпляр … был изменен или удален другой транзакцией”.  Это один из механизмов hibernate по поддержке консистентности данных.

При сбросе кэша в БД, hibernate вначале выполняет все вставки новых объектов, потом все изменения существующих объектов и потом все удаления удаляемых объектов.


6.6. Кэшируемые поля ORM объекта

В кэше находятся все поля ORM объекта, это важный момент. При первом разыменовании ссылки, в результате выполнения точечного запроса к БД, будет помещен в кэш весь ORM объект (если ранее он не был закэширован). Второе и третье разыменование этого или других полей уже не будет вызывать обращение  БД, все данные будут браться из кэша. 


Пример PL+
	r_md ref [MAIN_DOCUM];
       vc_code varchar2(25);
	vc_nazn_code varchar2(35);
      
       begin
	r_md := 3238811228;
	vc_code := r_md.[CODE];
	vc_nazn_code := r_md.[NAZN_CODE];
       …
       
соответствующий java код, фрагмент
       R_MD.assign(new ru.cft.platform.business.orm.MainDocum.Ref(new Number( 3238811228L)));
	VC_CODE.assign(R_MD.getCode());
	VC_NAZN_CODE.assign(R_MD.getNaznCode());

Включив логирование hibernate, видим один запрос в БД
        select maindocum0_.id as id2002_0_, maindocum0_.sn as sn2002_0_, maindocum0_.su as su2002_0_, maindocum0_.STATE_ID as STATE5_2002_0_..... from "Z#DOCUMENT" maindocum0_ inner join "Z#MAIN_DOCUM" maindocum0_1_ on maindocum0_.id=maindocum0_1_.id where maindocum0_.id=? and maindocum0_.CLASS_ID='MAIN_DOCUM'


6.7. Кэш первого уровня

При работе с hibernate кэш первого уровня используется всегда, отключить его нельзя.
В кэш первого уровня помещаются все объекты, загруженные или созданные в пределах одной сессии hibernate. Количество объектов, которые могут быть помещены в кэш, сейчас зафиксировано в размере 200 экземпляров.
Объект остаётся в кэше первого уровня до тех пор, пока:
* либо сессия не будет закрыта
* либо не будет удален принудительно командой
* либо не будет вытеснен. Политика вытеснения (удаления) – LRU (Least Recently Used) удаляются самые давно используемые объекты.


6.8. Кэш второго уровня

Кэш 2 уровня (межсессионный кэш) является необязательным, в отличии от кэша 1 уровня. Настраивается в разрезе ТБП путем добавления в файл настроек ORM – config_orm.xml. 
* Расположение файла настроек и синтаксис описаны в файле “Инструкция по переводу (установке) ЦФТ-Банк на архитектуру 2MCA DBI.pdf”, входящего в поставку  ЦФТ Банка.
* Добавлять надо только родительский ТБП, т.е., например, в случае, если надо кэшировать ТБП “Физические лица” (CL_PRIV), нужно добавить в настройку только родительский ТБП  “Клиенты” (CLIENT) и будут кэшироваться все клиенты. 
* Помимо короткого имени ТБП в настройке нужно указать стратегию кэшированию (READ_ONLY, NONSTRICT_READ_WRITE, READ_WRITE): 
READ_ONLY -  стратегия используется для кэширования неизменяемых данных. Можно указывать, если данные в ТБП никогда не меняются, либо гарантированно меняются (причем в обход hibernate, т.к. при попытке изменений через hibernate он сгенерирует исключение) в технологический перерыв, после которого производится рестарт всех СП. Стратегия позволит избежать накладных расходов на синхронизацию кэша.
NONSTRICT_READ_WRITE - стратегия предполагает, что данные могут изменяться, но изменения редки. Нет строгой синхронизации между БД и кэшем, что может привести к расхождениям, если данные в базе данных изменились, но кэш не был обновлён. 
READ_WRITE - стратегия поддерживает строгую синхронизацию между кэшем и БД. При каждом изменении данных кэш синхронизируется, чтобы избежать чтения устаревших данных. Для реализации этой стратегии используется механизм блокировки (locking). Данная стратегия строго не рекомендуется :
* синхронизации кэша между СП нет, а как правило, развернуто будет более 1 СП
* штатная работа кода допускает изменение БД в обход hibernate

На СП установлены следующие настройки кэша 2 уровня:
* Максимальное количество элементов - 1 000 000.
* Время, в течение которого объект может находиться в кэше перед тем, как будет признан устаревшим и удалён или обновлён - 5 минут.
* Политика вытеснения (удаления) объектов из памяти, когда достигает своего максимума лимит, выделенной для кэша, – LRU (Least Recently Used) удаляются самые давно используемые объекты.

Кэшируются не все экземпляры ТБП, а только те, к которым было обращение.
Экземпляр будет перекэширован спустя 5 минут, только если к нему будет обращение. При отсутствии обращения, он будет вытеснен по достижению порога 1млн записей.

6.9. Сессии

Важно. Говоря о кэше 1 и 2 уровней, подразумевается кэш сессий hibernate. Не прикладных сессий и не сессий БД. 
В общем случае, 1 http запрос от клиента (Навигатор, web Навигатор) - это 1 сессия hibernate. Один запрос – это, например, факт запуска операции. Когда будет изменено валидируемое поле экранной формы или нажата кнопка ОК – это уже другой http запрос и другая сессия hibernate.
После окончания работы с сессией hibernate, она удаляется со всем своим кэшем 1 уровня.

6.10. Обращение к кэшу hibernate (ORM), чтение

Разыменование ссылки является обращением к полям ORM объекта во всех случаях, независимо от того, разыменовывается переменная типа “ссылка” или происходит разыменование ссылки в курсоре. При этом всегда происходит обращение к кэшу hibernate и, возможно, выполняется точечный запрос к БД.
Примечание. Получение ID из переменной типа “ссылка” не является обращением к кэшу hibernate.


Пример PL+ кода c переменной типа “ссылка”

	vc_code := r_md.[CODE];
end;

// выполняется обращение к кэшу hibernate для получения реквизита CODE ORM объекта ТБП ::[MAIN_DOCUM]

6.11. Обращение к кэшу hibernate (ORM), изменение

Присвоение значений полям переменной типа “ссылка” является обращением к полям ORM объекта и фактически является ручным обновлением кэша. Аналогично происходит, когда выполняется точечный update по id

PL+ код
	r_md ref [MAIN_DOCUM];
begin
	r_md.[CODE] := vc_code;
	r_md.[NAZN_CODE] := vc_nazn_code;

соответствующий java код, фрагмент
// присвоение значения полям ORM объекта ТБП ::[MAIN_DOCUM] 
		R_MD.setCode(VC_CODE);
		R_MD.setNaznCode(VC_NAZN_CODE);
Еще пример обновления объекта ORM в кэше, когда выполняется точечный update по конкретному экземпляру
	r_md ref [MAIN_DOCUM];
begin
	r_md := 3238811228;
	update x(x.[NAZN_CODE]=vc_nazn_code) in ::[MAIN_DOCUM]	where  x = r_md;

6.12. Обращение к кэшу hibernate (ORM), вставка

Быстрым и оптимальным способом вставки новых данных с использованием hibernate является использование модификатора insert. По мере накопления изменений в кэше, hibernate будет пачками сбрасывать новые данные в БД

пример PL+
	tst_obj [TST_IMP_FMS];
begin

	for i in 1 .. 1000 loop
		tst_obj.[SER]:=to_char(i);
		::[TST_IMP_FMS]%insert(tst_obj);
	end loop;

6.13. Рекомендации по помещению ТБП в кэш второго уровня

Рекомендуется помещать ТБП в кэш второго уровня (межсессионный кэш) если:
* частота использования ТБП больше раза в секунду в работе кода в одной сессии
* данные ТБП не меняются, либо редко меняются. Например, справочные ТБП. 
Если данные редко меняются, то либо допустимо работать с устаревшими данными, т.к. кэш на каждом СП перечитывается раз в 5 минут, либо изменение кэшируемых данных производится в технические перерывы, когда прикладной код не работает.
* ТБП не должен содержать LOB реквизиты
