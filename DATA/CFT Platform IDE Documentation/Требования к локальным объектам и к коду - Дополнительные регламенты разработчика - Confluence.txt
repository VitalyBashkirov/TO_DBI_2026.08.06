ЭКРАННЫЕ ФОРМЫ ОПЕРАЦИЙ
    1. При оформлении экранных форм придерживаться общепринятых размеров контролов.
    2. Располагать однотипные контролы поблизости друг от друга. Например, кнопки под кнопками, надписи под надписями - выравнивая по ширине.
    3. Запрещено без особой на то причины изменять устанавливаемые по умолчанию шрифты и другие свойства контролов.
    4. Располагать кнопки "OK" и "Отмена" внизу экранной формы. При большой ширине окна - выравнивать по правому краю.
5. Необходимо устанавливать и упорядочивать порядок обхода элементов при разработке и изменении экранной формы соответственно правилу: слева направо, сверху вниз. Для этого удобно использовать признак "Авт. установка порядка движения". В исключительных случаях порядок обхода может быть отличен от стандартного, о чем должно быть обязательно упомянуто в пол ьзовател ьской документации.
6. Экранная форма не должна превышать размер 1024*768, т.к. реальный размер формы в пикселях при ее отображении Навигатором зависит от размера шрифта, установленного в Windows. Разработка ведется с условием, что формы в Навигаторе будут отображаться у пользователя, у которого в Windows выставлен шрифт «Normal size» (DPI=96). Размер формы при разработке контролируется разработчиком с помощью сервиса «Просмотр->Линейка» редактора экранных форм. В исключительных случаях для служебных операций форма может иметь больший размер.

Дело в том, что если их нет, то только в той схеме, где вы сейчас работаете). После добавления такого нового умолчательного параметра не должна меняться логика работы операции при вызове без задания этого параметра по сравнению с предыдущим вариантом кода (когда этого параметра вообще не было). Возможны исключения при обоснованной необходимости.
    2. При обработке в теле параметра типа массив либо не использовать оператор присваивания в значение реквизита, либо проверять на значение null.
3. При использовании параметров, имеющих тип логика и размещенных на экранной форме операции, обязательно определять их значение по умолчанию (true или false) в секции "DEFAULT" валидатора.

Причина данного ограничения в том, что в общем случае при работе пользователя через 3х-уровневую систему нет выделенной сессии с СУБД Oracle. При необходимости получения данных происходит обращение к Серверу Приложений (СП), который предоставляет для выполнения свободную сессию из пула сессий. По окончании выполнения запроса сессия возвращается в пул и может быть переиспользована другими пользователями. Исключением из этого правила является работа в форме операции - с момента запуска пользователем первой формы операции и до закрытия последней формы операции Oracle-сессия закрепляется за конкретным пользователем. По окончании диалога с пользователем сессия так же возвращается в пул сессий СП. При этом при возвращении сессии в пул СП производит принудительный сброс состояния пакетов.
Исходя из этого видно, что выполнение операции типа «Фильтр» (отработка секций валидации и тела) и выполнение выборки данных из представления (например, при последующем обновлении по F5) в общем случае будет происходить в разных Oracle-сессиях. Для того чтобы операция типа «Фильтр» работала корректно и в случае установки глобальных переменных пакетов, АРМ «Навигатор» запоминает значения параметров операции, введенных пользователем (те, контролы которых присутствуют на форме операции), и производит вызов тела операции с запомненными параметрами операции (последовательность: <вызов умолчательного валидатора> - <установка значений параметров операции, введенных пользователем> - <вызов тела операции>) перед выборкой данных из представления. В противном случае, пришлось бы с момента исполнения операции типа «Фильтр» и до момента ухода пользователя из представления с примененным фильтром, удерживать сессию закрепленной за конкретным пользователем, что противоречит требованию снижения нагрузки на СУБД Oracle.
Следует избавиться от вызова функции USER в условиях и источниках данных «простых» представлений. Данная ограничение связано с тем, что функция USER СУБД Oracle при работе в 3х-уровневой системе будет возвращать имя пользователя-посредника (обычно APP_SRV, под которым Сервер Приложений устанавливает соединение), а информация о том, какой субъект доступа выполняет операцию, может быть получена только через обращения к ТЯ. Исправлять на ::[RUNTIME].[STDLIB].userid

Исключением являются операции-расширения, наследующие дистрибутивную логику. Обоснование запрета: если такие переменные будут использоваться в теле операции, то, при вызове операции из кода, придется предварительно задавать значения таких переменных, что уменьшает удобство написания кода и повышает вероятность ошибки.К тому же, в отличие от параметров операции, такие переменные сохраняют свои значения на протяжении работы пользо вательской сессии, т.е. операция становится statefull, что делает поведение кода менее предсказуемым и усложняет диагностику возникающих проблем. Если все же необходимо сделать операцию statefull, то можно использовать локальную переменную с двумя функциями/процедурами.
