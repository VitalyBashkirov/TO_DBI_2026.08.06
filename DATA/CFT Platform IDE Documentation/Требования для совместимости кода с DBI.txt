2. Системные таблицы и представления ТЯ
Если таблице ТЯ есть соответствующий метакласс, то обращение должно выполняться именно через метакласс. В случае, если необходимый ТБП отсутствует в модели или не хватает каких-то реквизитов, необходимо обратиться за консультацией в ЦФТ.
Неверно
select s (s.[NAME]) in states%rowtype where s.[id] = ref_doc%state into st;
Верно
select s (s.[NAME]) in :: [STATES] all where s%id = ref_doc%state into st;
Допускается обращение к метаданным через системные модификаторы (%statename, %classname,…)но с ограничениями аналогичными вычисляемым реквизитам и UDF (см. пункт 8).

3. Псевдоколонки Oracle
Обращение к псевдоколонкам Oracle OBJECTID, OBJECT_VALUE, ORA_ROWSCN, ROWID, ROWNUM, XMLDATA недопустимо, так как в PostgreSQL их нет. Нужно избегать их использования. Вместо них, если необходимо, нужно писать прикладной код, дублирующий их логику работы, либо вводить в ТБП дополнительные реквизиты (если это не дистрибутивный объект).
Недопустимо
select d(d%rowid)
in	::[F_120_DETAIL]

into tIData;
Вместо этого, можно использовать, например, такую конструкцию
select d(d%id)
in	::[F_120_DETAIL]
where	d.[PARAM] = ref_param
into tNData;

6. Приведение к компиляции внешних соединений (outer join) в ANSI SQL
? Для хранилищ в формате А2 (zip) все новые и модифицируемые операции/представления должны содержать аннотацию @generate_ansi]oins(true). Явные внешние соединения, описываемые ранее константой (true), должны быть написаны с использованием синтаксиса ANSI SQL.

Требование следует выполнять с учетом особенностей применения (см. ниже).
Требование применимо для элементов модели, в которых нет внешних соединений старого вида (true). 7. Ограничение выборки fetch вместо rownum
Для ограничения выборки вместо псевдоколонки "rownum" следует использовать конструкцию "fetch X".
вместо конструкции вида
select p(p)
in :: [PRICE_LIST] all
where	p.[CODE] = upper(pCode) and
          rownum < 2
into vRef;
следует писать
select p(p)
in ::[PRICE_LIST] all
where p.[CODE] = upper(pCode) fetch 1
into vRef;
Запрещается в подзапросе конструкции exists использовать fetch, так как это приведет к полной выборке по подзапросу, а затем только ограничению строк выборки подзапроса.
Если встречается безусловный выход из курсора цикла (конструкция exit), то настоятельно следует использовать fetch в курсоре. Это критично для Java, так как СП не будет выбирать по одной строке, он сразу "выдернет" 100 строк из БД. А если разработчиком заложена такая простая конструкция, что ему достаточно первой строки, то надо об этом "сообщить" Java с помощь оператора fetch.
Пример как нельзя:
begin
for (select u(u.[DATE_BEGIN] : C_D1 ,u.[DATE_ENDING] : C_D2 ,u.[DATE_CLOSE] : C_CLOSE ,u.[NUM_DOG] : C_NUM_DOG)
           in ::[RKO]
where u.[ACCOUNT] = p_acc_id order by u.[DATE_BEGIN]) loop
      v_dBeg := u.C_D1;
      v_dEnd := u.C_D2;
      v_dColose := u.C_CLOSE;
v_Num := u.C_NUM_DOG; exit;
   end loop;
end;
Пример исправления:




























begin
   for (select u(u%rowtype)
in (select u(u.[DATE_BEGIN] : C_D1 ,u.[DATE_ENDING] : C_D2 ,u.[DATE_CLOSE] : C_CLOSE ,u.[NUM_DOG] : C_NUM_DOG)
in ::[RKO]
           where u.[ACCOUNT] = p_acc_id
           order by u.[DATE_BEGIN])
fetch 1) loop
      v_dBeg := u.C_D1;
      v_dEnd := u.C_D2;
      v_dColose := u.C_CLOSE;
      v_Num := u.C_NUM_DOG;
      exit;
   end loop;
end;
Также следует учитывать особенности работы fetch в отличие от rownum. Агрегатные/оконные функции: sum, min, max, avg, count, listagg и т.д. first_value/last_value/... over ...- обрабатывают весь объем данных, только потом ограничивается количество строк

fetch 1

8. В SQL-запросах использование функций PL/Plus бизнес-логики (UDF - User-Defined Functions) допускается лишь со следующими ограничениями:
Для операций запрещено использование UDF:
в запросе верхнего уровня с UNION;
в подзапросах;
в выражениях;
с выражениями в параметрах
в условии, группировке и сортировке;
определенных в самой операции.
Таким образом, разрешается использовать UDF (только определённые в другой операции) только в select-листе запроса верхнего уровня без UNION и без участия в выражениях и без выражений в параметрах.
Для представлений правила те же, дополнительно будут ограничения функциональности:
      • не будет работает сортировка по колонке (ошибка не будет выдана);
      • не будет работать фильтр (будет ошибка выполнения);
      • для колонки с типом timestamp не определяется тип в IDE, т.е. невозможно штатно задать формат даты;
      • статистика по вычисляемой колонке с UDF не поддерживается (будет показана ошибка в АРМе Навигатор);
      • для вычисляемых колонок-массивов, возвращаемых UDF, не поддерживается подсчет точного количества записей;
• не поддерживается вычисление колонок REF$ (нет корректной диагностики ошибки, представление не будет работать корректно);
      • не поддерживаются колонки с базовыми типами "OLE" и "TABLE";
      • не будет работать доступ по реквизиту для вычисляемой колонки.
































Пример
type main is select a( ::[RUNTIME].[F].a_saldo(sysdate, a, a.[RECORDS]) : C_SALDO1,--,	,	..

::[RUNTIME].[F].a(::[AC_FIN].[LIB].getValue(a%id)) : C_SALDO22, -- -	( - UDF)
       coalesce(::[RUNTIME].[F].a_saldo(sysdate, a, a.[RECORDS]), 0) : C_SALDO2,--

14. Арифметические операции с датами в запросах
Допускается использовать в запросах арифметические операции дат как с числами, так и с интервалами.
При вычитании дат необходимо учитывать тип возвращаемого значения (Oracle DATE-DATE = INTEGER, PG TIMESTAMP- TIMESTAMP=INTERVAL)
Неверно
select x(to_date('02.11.2023', 'dd.mm.yyyy') - to_date('01.11.2023', 'dd.mm.yyyy'))
in dual%rowtype
where to_date('02.11.2023', 'dd.mm.yyyy') - to_date('01.11.2023', 'dd.mm.yyyy') <= 1
into number;
Верно
select x(to_number(to_date('02.11.2023', 'dd.mm.yyyy') - to_date('01.11.2023', 'dd.mm.yyyy'))) in dual%rowtype
where to_number(to_date('02.11.2023', 'dd.mm.yyyy') - to_date('01.11.2023', 'dd.mm.yyyy')) <= 1 into number;
При этом необходимо учитывать, что ТЯ автоматически приводит интервал к строке. Приведение интервала к строке в Postgre по умолчанию осуществляется с округлением в меньшую сторону до целого числа дней.
Внимание! Использование в interval 'MONTH', 'YEAR' приводит к ошибкам. Необходимо использовать либо interval('1', 'DAY') *количество, либо функцию add_months.
Пример
where x.[DATE] + interval('1', 'DAY') > p_date
where x.[DATE] + interval('1', 'DAY')*k > p_date
15. Временные таблицы
1) Создание ТБП с признаком "на сессию" и на "транзакцию" выполняется как и раньше. Синтаксис есть в документации А2.
2) В прикладном коде перед первым обращением к временной таблицы следует вызвать ::[RUNTIME].[STORAGE_MGR]. init_temp_table(p_class_id string);
Зачем?
::[RUNTIME].[STORAGE_MGR].init_temp_table нужна для создания временной таблицы в PostgreSQL, т.к. в этой БД временная таблицы создаются в каждой сессии отдельно. Если таблица уже существует, ошибки не будет, т.к. в PG при создании таблицы в синтаксисе есть операнд IF NOT EXIST. Для Oracle эта функция не будет делать ничего, пустышка.
Для таблицы "на сессию" так же следует её предварительно очистить, так как СП может выделить чужую сессию, где могут остаться данные.
3) Для таблиц "на сессию" может понадобиться удержать сессию за собой, чтобы СП не отдал её другому. Для этого используются команды
executor.set_context('LOCK_SESSION', 1 ); --
executor.set_context('LOCK_SESSION', 0 ); --

В операции типа "фильтр" функция отбирает экземпляры по какому-то условию.
Выполняем выборку, вставляем во временную таблицу, потом в представлении используем эти данные.     В режимах 2MCA_Proxy, 2MCA, DBI операция-фильтр автоматически выполняется перед выборкой данных представления в той же сессии что и выборка данных, т.е. представление отработает корректно.

16. Триггеры
Триггеры базы данных относятся к серверному коду и возможны к использованию только для Платформы 1 и Платформы 2МСА. Для архитектуры DBI есть возможность использовать операции типа Триггер, но они не совместимы с Платформой 1.
Поэтому:
     1. Требуется дублировать реализацию триггеров через операции, при миграции на DBI триггеры в БД будут отключены
2. Можно отказаться от триггеров и прописать действия в программном коде. Например перенаправить все действия через прикладные функции/процедуры/операции. Это зависит от задачи.
     3. Если делать операцию-триггер, то поддерживать нужно будет два вида триггеров, пока Платформа 1 не уйдет в небытие.
В DBI триггер по сути будет операцией и будет иметь java-реализацию, будет вызываться средствами ТЯ при действиях над экземплярами.
Т.е. при update/insert/delete на SQL такой триггер не сработает, а при изменениях средствами PL+ сработает.
Поэтому для правильной работы триггеров-операций в DBI необходимо проводить анализ программного кода и:
     1. либо исключать прямые изменения таблиц в коде;
     2. либо такие изменения снабжать принудительным выполнением кода из триггера
Для реализации Oracle необходимо создать операцию триггер (в данном примере это TVR_TRIG), с вызовом ее из триггера Oracle (в данном примере это USR_TVR_TRIG)

17. Функциональные реквизиты в SQL запросах
Допустима возможность обращения к полю «Значение» функционального реквизита в select list запроса верхнего уровня (из-за ограничений UDF). Во всех остальных местах недопустимо использование функциональных реквизитов без секции «SQL значение». По возможности, необходимо заполнять секцию «SQL значение» там, где это возможно.
Если реквизит участвует в условии и у него есть SQL значение, то если это outer join, то вероятнее всего при создании представления будет возникать ошибка:
ORA-01799: a column may not be outer-joined to a subquery Cause: <expression>(+) <relop> (<subquery>) is not allowed.Action: Either remove the (+) or make a view out of the subquery. In V6 and before, the (+) was just ignored in this case.
Рекомендация: делать явный join, перенося логику вычисления реквизита прямо в запрос.
18. Иерархические запросы






































Для реализации иерархических выборок использовался синтаксис «connect by». Начиная с ТЯ 7.6.9.2 для той же цели нужно использовать CTE (WITH [RECURSIVE]) т. к. данная конструкция описана в ANSI SQL и поддержана в PLPLUS.
Ограничения:
     1. Иерархические запросы по метаданным под запретом.
2. Внутри выражения WITH нельзя использовать колонку вышестоящего запроса или колонку таблицы, которая соединяется на уровне конечного запроса with. Например, нельзя сделать колонку-подзапрос, которая зависит от данных основного запроса. Проявляется в SQL в виде ошибки компиляции.
     3. Порядок выборки данных отличается от connect by.
     4. Нет аналога nocycle. Ограничение от зацикливания надо указывать в секции where.
Пример из DEPART.LIB:
Было
select d_(d_.ID : D_ID) in (
     select d(d%id : ID, d.[HIGH] : HIGH) in ::[DEPART] connect by d%id = prior d.[HIGH] start d%id = dep
) where d_.[HIGH] is null and rownum < 2 into high_dep;
Стало
with recursive t(id, high) as (
    select x(x%id : id, x.[HIGH] : high) in ::[DEPART] where x%id = dep
    union all
    select x(x%id : id, x.[HIGH] : high) in ::[DEPART] join (t : t2) on t2.high = x ) select t1(t1.id) in t where t1.high is null fetch 1 into high_dep;

29. Прерванная транзакция
При разработке необходимо учитывать, что исключениями генерируемые БД прерывают транзакцию, не путать с исключениями в процедурном коде (например: NO_DATA_FOUND, TOO_MANY_ROWS, OBJECT_NOT_FOUND). Для продолжения работы с БД необходимо откатить транзакцию на точку сохранения, установленную до возникновения ошибки.
Конструкция when others перехватывает все исключения , в том числе и генерируемые БД, поэтому &rb или raise обязателен.
execute is
    nCnt number;
begin
??
select x(to_number(to_date('02.11.2023', 'dd.mm.yyyy') - to_date('01.11.2023', 'dd.mm.yyyy'))) indual%rowtype
where to_date('02.11.2023', 'dd.mm.yyyy') - to_date('01.11.2023', 'dd.mm.yyyy') <= 1 (ошибка приведения типов) into nCnt;
дальше выполняется процедурный код без обращения к БД. Если обратиться к БД, то будет ошибка: current transaction is aborted, commands ignored until end of transaction block
end;
execute is
    nNum number;
begin
?.
begin
&sp(point1)
select x(to_number(to_date('02.11.2023', 'dd.mm.yyyy') - to_date('01.11.2023, 'dd.mm.yyyy'))) indual%rowtype
where to_date('02.11.2023', 'dd.mm.yyyy') - to_date('01.11.2023', 'dd.mm.yyyy') <= 1 (ошибка приведения типов) into nCnt;
exception
when others then
    - для продолжения работы
    &rb(point1)
end;
end;

33. Execute immediate
Учитывая основные требования регламентов, в случае необходимости использования execute immediate требуется писать запрос таким образом, чтобы он мог одинаково проигрываться в разных средах (Oracle, PG)
execute immediate 'truncate table Z#DBI_TEST'; Будет работать в Oracle но вызовет ошибку в PG так как имя таблицы не экранировано.
execute immediate 'truncate table "Z#DBI_TEST"'; Будет работать одинаково и в Oracle и PG.
execute immediate 'alter session enable parallel dml'; Не будет работать в PG, так как нет поддержки такого синтаксиса
execute immediate( 'begin :1:= some_function end;') using out v_test; Не будет работать в PG так как синтаксис анонимного блока отличается от синтаксиса Oracle
34. Пустая строка и null
В PostgreSQL пустая строка ‘’ не является null (в отличии от oracle)
Oracle
SQL> select case when ” is null then 'yes' else 'no' end from dual;
case
yes
PostgreSQL
cft14=# select case when '' is null then 'yes' else 'no' end;
case
no
Это надо учитывать при написании кода запросов к БД.
