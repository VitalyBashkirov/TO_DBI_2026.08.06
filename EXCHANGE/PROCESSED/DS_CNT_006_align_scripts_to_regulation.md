# DS_CNT_006. Приведение скриптов к регламенту DS_CNT_000

## Цель
Привести скрипты этапов 001–005 к единому регламенту
`EXCHANGE\DS_CNT_000_regulation.md`:
- имена файлов `run_cnt_<NNN>_nightly.cmd` (на основе
  `tools\_template_nightly.cmd`);
- логи/коды/ошибки/lock по регламенту;
- проверка предыдущего этапа;
- проверка YAML, каталогов, записи в `logs`;
- проверка MCP-конфига (exFAT-вариант, вместо ACL) для этапа 004.

В DS_CNT_001_report указаны `tools/_cnt_001_main.py`,
`tools/run_cnt_001.cmd` — не по регламенту. Аналогичные отклонения
могут быть в этапах 002–005.

## Предусловия
- DS_CNT_000 выполнен: `tools\_template_nightly.cmd` создан.
- DS_CNT_000a выполнен (регламент дополнен пунктом про exFAT).
- DS_CNT_001..005 выполнены (полностью или частично).
- DS_CNT_004a и DS_CNT_005a — желательно выполнены. Если нет —
  dry-run (шаг 5) может быть невозможен, зафиксировать в отчёте.
- Специфика `:run_main` — в `DS_CNT_001_005_ai_continue_setup.md`,
  разделы «Специфика `run_cnt_<NNN>_nightly.cmd`» для каждого этапа.
  KODA переносит специфику без изменений.
- Регламент: `EXCHANGE\DS_CNT_000_regulation.md` (разделы 2–7,
  включая п. 1.11 про exFAT).

## Терминология
- CNT = Ai-Continue.
- `F:\TO_DBI\logs` — логи операций АРМа. `EXCHANGE\bot.log` — лог АРМа.

## Матрица доступа (роль АРМ для CNT)
- чтение: DATA, EXCHANGE, PATCH_IN;
- запись: logs, PATCH_OUT;
- запрет: запись в DATA, EXCHANGE, PATCH_IN.

## Шаги

### Шаг 1. Инвентаризация текущих скриптов
Проверить наличие и содержимое:
```
dir F:\TO_DBI\tools\*cnt* /b
```
Ожидаемо: `_template_nightly.cmd`, `run_cnt_000_nightly.cmd`,
`run_cnt_001..005_nightly.cmd`.

Если есть `run_cnt_001.cmd`, `_cnt_001_main.py` и т.п. — зафиксировать
как отклонения.

`run_cnt_000_nightly.cmd` — **не изменять**. Если требуется обновление
(например, новый шаблон) — зафиксировать в отчёте как отдельную задачу.

Проверить, что `_template_nightly.cmd` содержит:
- проверку предыдущего этапа (правка 3.7 в DS_CNT_000);
- проверку записи в `logs` через `_write_test.tmp` (правка 3.1).
Если нет — обновить шаблон до актуальной версии.

### Шаг 2. Привести этапы 001–005 к регламенту
Для каждого этапа <NNN> = 001..005:
- создать `tools\run_cnt_<NNN>_nightly.cmd` на основе
  `tools\_template_nightly.cmd`;
- `:check_deps`:
  - проверка `ds_cnt_<NNN-1>.exit` = 0 (код 1, кроме 000);
  - YAML-синтаксис `config.yaml` (код 2);
  - Ollama и модели (код 3);
  - каталоги `logs`, `tools`, `EXCHANGE\OUTBOX` (код 4);
  - запись в `logs` через `_write_test.tmp` (код 4);
- `:run_main`: специфика этапа — в `DS_CNT_001_005_ai_continue_setup.md`,
  разделы «Специфика `run_cnt_<NNN>_nightly.cmd`» для каждого этапа.
  KODA переносит специфику без изменений.

  Если `DS_CNT_001_005_ai_continue_setup.md` отсутствует — специфика
  `:run_main` берётся из соответствующих отчётов
  `DS_CNT_001..005_report.md`. Если и их нет — останов, эскалация.

  **Для этапа 004:** специфика `:run_main` в exFAT-версии —
  в `DS_CNT_004a_complete_mcp_config.md`, раздел «Шаги».
  KODA переносит проверки MCP-конфига (`MCP_SHELL_ALLOW`,
  `MCP_GIT_MODE`, `MCP_FS_ROOTS_RW/RO`) вместо проверок ACL
  (`icacls`).

- лог → `F:\TO_DBI\logs\ds_cnt_<NNN>.log`;
- код → `F:\TO_DBI\logs\ds_cnt_<NNN>.exit`;
- ошибки → `F:\TO_DBI\logs\ds_cnt_<NNN>.err`;
- lock → `F:\TO_DBI\logs\ds_cnt_<NNN>.lock`.

### Шаг 3. Удалить/архивировать старые скрипты
- `tools/run_cnt_001.cmd`, `tools/_cnt_001_main.py` и аналогичные —
  переместить в `tools\_archive\` (не удалять без согласования).
- Имя файла сохраняется; при необходимости добавить дату:
  `run_cnt_001_<YYYYMMDD>.cmd`.
- Проверить, что старые скрипты не упомянуты в
  `DS_CNT_000_regulation.md` и в `agents-short.md`.
  Если упомянуты — обновить упоминания.
- Зафиксировать в отчёте: что перемещено, куда.

### Шаг 4. Обновить лог-файлы
- Старые логи (`logs/cnt_000_03102026_030557.log` и т.п.) —
  по умолчанию переместить в `logs\_archive\`.
  Оставить — только по указанию Администратора АРМа.
- Новые логи — по регламенту: `ds_cnt_<NNN>.log`.
- Если архивация логов затрагивает отчёты 004/005 — обновить их.

### Шаг 5. Проверить каждый скрипт (dry-run)
Для каждого <NNN> = 000..005:
- запустить `tools\run_cnt_<NNN>_nightly.cmd`;
- проверить: `ds_cnt_<NNN>.exit`, `ds_cnt_<NNN>.log`,
  `ds_cnt_<NNN>.err`, `ds_cnt_<NNN>.lock` (удалён);
- убедиться, что цепочка 000 → 001 → … → 005 проходит без обходов.

Если 004a имеет статус «частично» (CLI недоступен) — dry-run 004
может не пройти проверку MCP-серверов. Зафиксировать в отчёте,
считать DS_CNT_006 «выполнено частично».

Если dry-run невозможно из-за невыполненных 004a/005a (нет `svc_mcp`,
нет CLI, нет MCP-конфига) — зафиксировать в отчёте, dry-run отложить
до завершения 004a/005a. В этом случае DS_CNT_006 считается
«выполнено частично».

### Шаг 6. Обновить `agents-short.md`
В разделе «Пакетный ночной режим (DS_CNT_000)» уточнить:
- скрипты этапов — `run_cnt_<NNN>_nightly.cmd`;
- старые скрипты — в `tools\_archive\`.

### Шаг 7. Обновить отчёты
- `DS_CNT_000_report.md` — дописать: скрипты приведены к регламенту,
  старые архивированы, dry-run пройден (или зафиксировано, что
  невозможно).
  Добавить в отчёт таблицу агрегации:

  | DS | Статус | Код | Отчёт |
  |---|---|---|---|
  | 001 | … | … | DS_CNT_001_report.md |
  | 002 | … | … | DS_CNT_002_report.md |
  | 003 | … | … | DS_CNT_003_report.md |
  | 004 | … | … | DS_CNT_004_report.md |
  | 000a | … | … | DS_CNT_000a_report.md |
  | 004a | … | … | DS_CNT_004a_report.md |
  | 005 | … | … | DS_CNT_005_report.md |
  | 005a | … | … | DS_CNT_005a_report.md |

- `DS_CNT_004_report.md`, `DS_CNT_005_report.md` — если архивация
  логов их затрагивает.
- `DS_CNT_006_report.md` — отдельный отчёт.

  `code_fixer.py` — не трогать.
- MCP shell и MCP-скрипт — не использовать.

10. Отчёт `DS_CNT_006_report.md` в OUTBOX.
