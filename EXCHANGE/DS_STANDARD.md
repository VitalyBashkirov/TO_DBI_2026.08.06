# DS_STANDARD — Стандарт оформления DS-заданий

**Версия:** 1.0 от 19.09.2026
**Назначение:** единый шаблон для всех DS-заданий. Сокращает объём каждой задачи в 3–5 раз.

---

## 1. Стандартная шапка

```
**Дата:** <ДД.ММ.ГГГГ>
**Автор:** DeepSeek
**Исполнитель:** KODA
**Тип:** <разведка | реализация | уточнение | feature>
**Приоритет:** <высокий | средний | низкий>
**Зависит от:** <DS_XXX или «нет»>
**Блокирует:** <DS_XXX или «—»>
```

---

## 2. Стандартные ограничения

Действуют по умолчанию, если в задаче не указано иное:

- Не коммитить без команды `GIT`.
- Не менять файлы вне списка «Что менять».
- Не трогать тесты вне указанного списка.
- Соблюдать протоколы DS_048/049/050/052.
- Запись в `EXCHANGE\bot.log`:
  `[ДД.ММ.ГГГГ ЧЧ:ММ:СС] DS XXX: <краткий итог>.`
- Отчёт — в `EXCHANGE\OUTBOX\DS_XXX_report.md`, UTF-8 без BOM.
- Если при реализации выявится расхождение с предположениями задачи — остановиться, доложить автору DS, не додумывать.

---

## 3. Стандартный формат отчёта

Если в задаче не указано иное, отчёт содержит **5 разделов**:

```
# DS_XXX — Отчёт

## 1. Что сделано
- <краткий перечень>

## 2. Изменённые файлы
- <путь> — <что изменено>

## 3. Результат тестов
- Тесты: N/N PASSED
- Регресс DS_032–DS_XXX: <результат>

## 4. Расхождения
- <если есть; иначе «нет»>

## 5. Артефакты
- <пути>
```

Расширенная структура — если задача специфична (разведка, feature с UI и т.п.). В этом случае в задаче указываются дополнительные разделы.

---

## 4. Стандартный шаблон «Разведка»

```markdown
## Разведка (стандарт)

1. Найти: <что> — где <каталоги/файлы>.
2. Собрать: <что именно> (определение, вызовы, контекст).
3. Воспроизвести: <баг/поведение> — <как>.
4. Зафиксировать: diff, MD5, факты.
5. Восстановить: если что-то менялось в ходе разведки.
6. Отчёт по стандарту (раздел 3) + дополнительные разделы (если указаны).
```

В задаче указываются отличия от шаблона: что искать, что воспроизводить.

---

## 5. Стандартный шаблон «Реализация»

```markdown
## Реализация (стандарт)

1. Создать/изменить: <список файлов>.
2. Реализовать: <суть> — API/поведение (см. DS_FILES.md, DS_CONTEXT.md).
3. Тесты: <список кейсов>.
4. Прогнать регресс.
5. Отчёт по стандарту.
```

В задаче — только отличия от шаблона: конкретные функции, конкретные кейсы, ссылки на `DS_FILES.md` / `DS_CONTEXT.md`.

---

## 6. Форматирование

Предпочтительно:

- Таблицы вместо длинных перечислений.
- JSON для схем данных (settings.json, API-контракты).
- Короткие списки вместо абзацев.
- Ссылки на `DS_CONTEXT.md` / `DS_FILES.md` вместо повторов.
- Аббревиатуры для известных терминов (после первого упоминания).

### Пример: длинное описание → таблица

**Было (10 строк):**

> Правило 1 — в GUI добавить чекбокс v53.
> Правило 2 — в GUI добавить чекбокс тдс.
> Правило 3 — в GUI добавить чекбокс тклоик.
> Правило 4 — в GUI добавить чекбокс PlpCheck.
> Правило 5 — состояние хранить в settings.json.

**Стало (5 строк):**

| # | Что | Где |
|---|-----|-----|
| 1 | Чекбокс `v53` | `_populate_rules_tree` |
| 2 | Чекбокс `тдс` | `_populate_rules_tree` |
| 3 | Чекбокс `тклоик` | `_populate_rules_tree` |
| 4 | Чекбокс `PlpCheck` | `_populate_rules_tree` |
| 5 | Состояние → `settings.json` | `save_settings` |

## 7. Чего избегать

- Повтор шапки — ссылка на этот файл.
- Повтор стандартных ограничений — ссылка на раздел 2.
- Повтор формата отчёта — ссылка на раздел 3.
- Длинные абзацы «обоснований» — 1–2 предложения максимум.
- Дублирование информации из `DS_CONTEXT.md` / `DS_FILES.md`.
- Пометки «Ревизия N» — они для истории, не для KODA.
- Фразы «важно», «критично», «обязательно» — если правило реально критично, оно выделяется структурно (раздел, тест).

## 8. Оценка экономии

| Приём | Экономия на задачу | Экономия на 10 задач |
|-------|--------------------|----------------------|
| Стандартная шапка | 15–20 строк | 150–200 |
| Стандартные ограничения | 10 | 100 |
| Стандартный отчёт | 15–40 | 150–400 |
| Ссылки на CONTEXT/FILES | 10–30 | 100–300 |
| Таблицы/JSON | 10–20 | 100–200 |
| Шаблоны разведки/реализации | 50–100 | 500–1000 |

## 9. Проверка перед публикацией

Перед публикацией DS в `INBOX\` автор обязан проверить:

- [ ] Шапка — по стандарту (раздел 1).
- [ ] Есть ссылка на `DS_CONTEXT.md` / `DS_FILES.md` (если они релевантны).
- [ ] Стандартные ограничения **не дублируются** — ссылка на раздел 2.
- [ ] Формат отчёта **не дублируется** — ссылка на раздел 3.
- [ ] Использованы **таблицы / JSON** вместо длинных перечислений (раздел 6).
- [ ] Нет «Ревизия N», «Важно:», «Критично:» (раздел 7).
- [ ] Если задача — разведка: использован шаблон из раздела 4.
- [ ] Если задача — реализация: использован шаблон из раздела 5.

Если хотя бы один пункт не выполнен — **переоформить** до публикации.

### Почему это важно

- **Экономия токенов.** Стандартные разделы (шапка, ограничения, формат отчёта) — **один раз** в этом файле, а не в каждой задаче.
- **Согласованность.** Все DS — **одного формата**. KODA читает быстрее.
- **Меньше ошибок.** Меньше повторов — меньше расхождений.
