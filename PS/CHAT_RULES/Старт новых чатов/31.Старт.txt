## НОВЫЕ ПРАВИЛА / УРОКИ ЧАТА 30

Зафиксированы в DS_STANDARD.md §6.6.1–§6.6.9.

### §6.6.1 — Урок FF: логирование внешних процессов

Start-Transcript в PS 5.1 НЕ перехватывает stdout/stderr внешних
процессов (python.exe, git.exe, ollama.exe). Их вывод не попадает
в лог-файл транскрипта.

Решение: для каждого вызова внешнего процесса:
    python tools\ai_local_worker.py --check 2>&1 | Out-Host
    git status -sb 2>&1 | Out-Host
    git log -1 --oneline 2>&1 | Out-Host

Расширяет Урок V (правило 62) и Урок T (правило 60).

### §6.6.2 — Урок GG: bot.log для DS без кода

Правило 29 (bot.log до коммита) обязательно для DS, меняющих
код/тесты/конфиги. Для DS без кода (гигиена, удаление файлов,
чистка .bak_, обновление документации) — bot.log НЕ ОБЯЗАТЕЛЕН.
Решение принимает Автор DS, фиксирует в отчёте.

### §6.6.3 — Уточнение правила 19: fail-fast return

Fail-fast return в PS-блоках допустим, если:
- return внутри if ($условие_ошибки);
- перед return Stop-Transcript | Out-Null;
- после return не остаётся полезной работы.

Иначе — правило 19 («никаких return») действует.

### §6.6.4 — Урок T расширен: NativeCommandError

PS 5.1 помечает любой stderr внешнего процесса как
«NativeCommandError», даже если это warning от git (LF/CRLF).
Ориентир — $LASTEXITCODE (должен быть 0). Не глушить через 2>$null.

### §6.6.5 — Обязательное логирование PS-блоков

Каждый PS-блок, выполняющий работу, ОБЯЗАН:
- начинаться с очистки PS\ (N7);
- содержать Start-Transcript -Path PS\<имя>.log -Force | Out-Null;
- заканчиваться Stop-Transcript + вывод пути к логу.

Исключение: тривиальные однострочные проверки.

### §6.6.6 — Урок HH: идемпотентность append-блоков

Любой PS-блок, дописывающий текст в файл, должен быть
идемпотентным. Перед записью — Select-String по сигнатуре.
Если найдено — fail-fast.

Инцидент DS_138b: случайный двойной запуск дал дубль
§6.6.1..§6.6.4, потом чинили вручную.

### §6.6.7 — Урок II: границы блоков в .md

При автоматическом поиске границ фрагмента в .md НЕЛЬЗЯ
полагаться на «ожидаемое» число пустых строк. Выводить ВСЕ
строки вокруг границы, проверять фактические индексы.
Если хотя бы одна проверка не совпала — fail-fast.

Инцидент DS_138b: первый fix-блок остановился на fail-fast
из-за неверного предположения о пустой строке.

### §6.6.8 — Урок JJ: формат bot.log

Перед append в bot.log — Get-Content -Tail 3, скопировать
фактический формат. Существующий формат:
    [YYYY-MM-DD HH:MM] DS_XXX: текст
Не append «по памяти». Проверять идемпотентность.

Инцидент DS_138b: строка записана без скобок и времени.

### §6.6.9 — Урок JJJ: -like в PS — wildcard

Оператор -like в PowerShell трактует [ ], * , ? как wildcard.
Если анкор содержит [ ] (Python-код: списки, срезы) —
WildcardPatternException.

Для проверки подстроки использовать МЕТОД .Contains():
    # ПЛОХО:
    if ($content -like ("*" + $old + "*")) { ... }
    # ХОРОШО:
    if ($content.Contains($old)) { ... }

Инцидент DS_141 Шаг 3: анкор с [sys.executable, ...]
упал на -like. Файл не пострадал (fail-fast).
