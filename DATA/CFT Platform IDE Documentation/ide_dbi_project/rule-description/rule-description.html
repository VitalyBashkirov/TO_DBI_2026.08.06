Обращение к статическому экземпляру
ACCESS_STATIC
JAVA PLSQL
Требование: необходимо подключение к Oracle схеме.

Статических экземпляров в системе очень мало, создаются они по флагу статического реквизита на ТБП, самый известный ТБП - это SYSTEM, и то только в части реквизита SYS_MAIN_VAL, но по коду часто еще обращаются, например к реквизиту OP_DATE. Проверка считывает из БД все реквизиты помеченные флагом статического и в случае диагностики обращения к такому реквизиту не считает это ошибкой, также не считает ошибкой обращение к любым полям ТБП SYSTEM(это хард код). Чаще всего, когда диагностируется обращение к статическому экземпляру в коде есть ошибка. Реализация проверки очень сложная из-за того, что мы не можем заглянуть в сгенерированную java или pl/sql, а пытаемся поймать на уровне PL+, если найдете кейсы без обращения к статическому экземпляру, но проверка будет ругаться, присылайте.
Пока известен один кейс некорректной диагностики, который не хочется учитывать в плагине. А именно:
Объявление переменной через var во вложенном блоке, т.е. типа такого:

declare
    a number := 1;
begin
    if a = 1 then
        var main_docum number; 
    end if;
    main_docum := 3;
end;

В данном примере грамматика IDE считает переменную main_docum классом, а не объявленной выше переменной, это видно если попытаться через ctrl провалиться в нее и только за счет этого пропускает данный синтаксис. А если бы у переменной было бы имя отличное от имени существующего класса, то валидатор xtext-а сказал бы что это не корректный код и не допустил бы к деплою.

Пример ошибки

            declare                    
        acc ref [AC_FIN];
    begin
        acc := ::[MAIN_DOCUM].[ACC_DT];
    end;
Пример исправления

            declare                    
        acc ref [AC_FIN];
        doc ref [MAIN_DOCUM];
    begin
        doc := ...;
        acc := doc.[ACC_DT];
    end;

Контроль использования аналитических функций совместно с fetch или exists
ANALYTIC_AND_FETCH_BAD_USE
JAVA PLSQL

Использование аналитических функций совместно с fetch или внутри exist приводит к увеличению времени работы запроса.
Причина - аналитическая функция при использовании fetch или exists применяется ко всем строкам запроса.
При этом сам fetch - это по сути тоже аналитическая функция: работает через row_number over (order by null) и он совместно с exists тоже читает весь результат запроса.

Метод проверки Проверка ловит конструкции fetch и exists.
Для exists проверяет, нет ли в основном селект листе аналитических функций.
Для fetch проверяет 2 кейса:
- не использован ли он внутри exists
- нет ли в головном селект листе функций агрегирования: count,sum,min,max при условии что в этом же селекте отсутствует секция group by, т.е. возвращаться будет всегда одна строка и не зачем там использовать fetch.
Пример ошибки

            select count(1) 
      from z#main_docum md, z#records r
     where r.c_doc = md.id
     FETCH FIRST 1 ROWS ONLY  

    select case when exists(select 1 from z#main_docum md, z#records r
                             where r.c_doc = md.id
                             FETCH FIRST 1 ROWS ONLY) then 1 end
      from dual

    select case when exists(select row_number() over (order by null) 
                              from z#main_docum md, z#records r
                             where r.c_doc = md.id) then 1 end
      from dual;
Пример исправления

            select count(1) 
      from z#main_docum md, z#records r
     where r.c_doc = md.id  

    select case when exists(select 1 from z#main_docum md, z#records r
                             where r.c_doc = md.id) then 1 end
      from dual

Анализ размерности стэка ошибки и поисковых строк для функций call_stack/error_stack
CALL_STACK_ANALYSIS
DBI JAVA

Анализ стека вызовов в целом является плохой практикой, при этом стеки вызовов в PL-SQL и Java могут отличаться из-за особенностей именования пакетов/классов, в том числе стеки могут иметь разный размер итогового текста. Поэтому запрещено анализировать стек вызовов в процедурном программном коде без указания достаточного размера стека(32000), также запрещено анализировать в стеке вызовов строки вида "Z#", "Z$".

Метод проверки Анализом стека вызовов считается сравнение utils.call_stack и utils.error_stack(с параметром p_stack = true, это значение по умолчанию) со строкой или поиск в них подстроки при помощи: =, case, like, regexp_like, instr, regexp_instr, replace, regexp_replace и их отрицаний без указания без указания значения параметра p_stack_size или если значение параметра не определено (переменная/функция и т.д.) или если значение параметра < 32000.
Особенности анализа поисковой строки:
- Для конструкций like, regexp_like, instr, regexp_instr, replace, regexp_replace ошибкой будет считаться ситуация когда поисковая строка содержит буквы или цифры, т.е. вызов вида instr(utils.call_stack, ':', -1) считается допустимым;
- В поисковой строке запрещено использовать "Z#", "Z$". Такие строки анализируются с учетом того что до и после них нет других символов без пробельных и знаков препинания. Примеры запрещенных строк: Z$, Z$DOC_TYPE_EDIT_AUTO, Z#DOC_TYPE#INTERFACE. Примеры разрешенных строк: IDX_Z#DOC_TYPE_CODE, ABZ#TEST
- Если поисковая строка не является литералом, а является переменной, функцией, в т.ч. конкатенацией значений (||) и т.д., то происходит попытка получить значение. Если значение не удалось вычислить, то это будет считаться ошибкой, так как строка может содержать любые символы.
Пример ошибки

            `if instr(utils.call_stack(), 'PUB_DEAL_OPER') < 1 then`                            
`if instr(utils.call_stack, 'Z$TRC_SECURED_SCAN.') = 0 then`
`if ::[RUNTIME].[UTILS].error_stack like '%(%.IDX_Z#REPS_CLIENT_INFO_CL_DT_S)%' then`
Пример исправления

            `if instr(utils.call_stack(32000), 'PUB_DEAL_OPER') < 1 then`                           
`if instr(utils.call_stack(32000), 'TRC_SECURED_SCAN.') = 0 then`
`if ::[RUNTIME].[UTILS].error_stack(true, 32000) like '%(%.IDX_Z#REPS_CLIENT_INFO_CL_DT_S)%' then`

Выявлять закомменитрованный код
CODE_IN_COMMENT
STYLE

Закомментированный код считается плохим тоном и запрещен в многих регламентах

Метод проверки Для получения текста для проверки берутся отдельно многострочные комментарии, однострочные склеиваются вместе, начиная с тех, которые начинаются на новой строке. Если комментарий начинается с мароса (#if, #elseif, #define и др.), такие комментарии игнорируются.
В тексте считается доля строк, оканчивающихся ";" и доля служебных слов, операторов PL+. Оба этих показателя учитываются с определенными весами. Если в тексте более 10% кириллицы, проверка не срабатывает.
Проверка может давать ложные срабатывания. Чтобы их точно исключить, можно добавить кириллицу.
Пример ошибки

            begin
        /* select x(1) in ::[XXX] 
         into  zzz;*/   
        null;
    end;
Контроль количества колонок в запросах
COLUMNS_LIMIT_EXCEEDED
DBI JAVA

Разыменование реквизита в hibernate может привести к join'ам таблиц из иерархии ТБП и выбору почти всех колонок из этих таблиц. Однако в PostgreSQL есть ограничение на максимальное число колонок в выборке - 1664. Запрос сломается, если число колонок превысит данное значение. Проверка выполняет анализ числа колонок в hibernate выборке.

Варианты исправления

  • Сделать родительский ТБП абстрактным (abstract class …)
  • Сделать дочерние ТБП самостоятельными
  • Убрать обращение к экземпляру родительского ТБП
  • Уменьшить количество колонок в таблице
    И т.д.
Метод проверки 1. Проходимся по всем дочерним ТБП относительно ТБП реквизита, к которому происходит обращение.
2. Поднимаемся по одной ветке вверх по иерархии наследования (от ТБП переменной/параметра) до самого далекого неабстрактного родителя.
3. Суммируем число столбцов в пройденных ТБП, учитывая системные колонки ID, SN, SU, CLASS_ID.
Иерархия всех ТБП формируется заранее в кэше.
Контролировать выражения поиска экземпляров на этапе компиляции на предмет полноты условий
COMPILE_MISSING_COND
JAVA PLSQL
Требование: необходимо подключение к Oracle схеме.

Данная проверка создана на основе представления о том как в системе организована работа со справочником "Универсальный справочник кодов/наименований"(UD_CODE_NAME), т.к. это самый отъявленный случай. Суть в чем, разработчик данного справочника заложил что наполнять его нужно по ключу из двух полей "Код"(CODE) и "Код справочника"(UD_CODE), но некоторые пренебрегают этим условием на этапе компиляции, программируя конструкции вида: ::[UD_CODE_NAME]([CODE] = ‘X’), и такое будет работать до тех пор пока какой-нибудь другой разработчик не добавит записи в этой справочник с другим значением UD_CODE, после этого у того кто написал выражение без условия на UD_CODE перестанет компилироваться операция, т.к. компилятор найдет 2 записи со значением X в поле CODE.
Также помимо проблем на этапе компиляции проверка еще может контролировать селекты(locate(exact), %locate(exact), select into) по ТБП с установленной уникальностью, у которых нет обработчика исключений TOO_MANY_ROWS или others и нет fetch. К таким конструкциям приравнивается ::[TBP](...) с отключенным рассчетом экземпляров через аннотацию @calculate.

Проверка умеет определять правила уникальности 2я способами:
- по уникальным индексам на таблицах(учитываются только не функциональные индексы, в ключе которого отсутствуют системные колонки, а также количество колонок больше одной)
- по ручному заполнению настройки

В проверке есть следующие настройки:
- Контролировать на основании уникальных индексов. Т.е. можно отключить общую логику с определением уникальности и вручную вести набор справочников для контроля;
- Контролировать полноту условий в конструкциях locate(exact), %locate(exact), select into(только из одного ТБП, без join-ов, group by, connect by). Т.е. если будет найдена такая конструкция и у нее будет отсутствовать блок fetch проверка еще проверит отсутствие обработчика исключений TOO_MANY_ROWS, если не найден ни того ни другого запустит проверку как будто это селект выполняемый на этапе компиляции. Эта же настройка влияет на проверку ::[TBP](...) если у операции будет установлена аннотация @calculate(false) или @calculate(classes:=false);
- Дополнительные ключи для контроля. С помощью данной настройки можно отключить контроль на основе индексов и контролировать например только справочник UD_CODE_NAME. Для этого нужно добавить следующую запись: UD_CODE_NAME;CODE,UD_CODE. Если контроль по индексам будет включен и в этом справочнике будет добавлена противоречащая запись, информация об индексах будет проигнорирована.

У проверки есть ограничения реализации в части:
- уникальности на основе составных реквизитов, т.е. например такое не будет работать: MAIN_DOCUM;CODE,KL_DT.0.2.ACCNUM. Связано это с тем что вложенность может быть большой и колонка в таблице может начать называться не так как атрибут, а на текущий момент мы в плагине не состыковываем поля индексов с атрибутами ТБП;
- Также не контролируется комбинации and/or.

Метод проверки Сначала в зависимости от настройки(проверять в locate и подобных), наличию fetch и обработчика исключений TOO_MANY_ROWS или others, отсекаются проверяемые конструкции. Далее из секции where выдергиваются все реквизиты, которые участвуют в формировании условий отбора. Если там встречается условие по модификатору %id, то проверка прекращается.
Если контролируемая конструкция не отсеклась на более раннем этапе, тогда в зависимости от настроек(смотреть на индексы, дополнительные ключи) строит ожидаемый набор реквизитов. Из полученных наборов удаляются атрибуты, которые есть в секции where и если после такой очистки массив ожидаемых реквизитов остался не пустой, тогда выдается исключение.
Пример ошибки

            ::[UD_CODE_NAME]([CODE] = ‘X’)
Пример исправления

            ::[UD_CODE_NAME]([UD_CODE] = ‘Y’ and [CODE] = ‘X’)
Контроль конкатенаций применяется для обеспечения эффективного использования памяти.
CONCAT_CONTROL
DBI

Проверка выявляет использование dbms_lob.writeappend, dbms_lob.write, dbms_lob.append, ||, concat для объектов clob и blob. В случае явного многократного использования(конкатенация в цикле без четкого условия выхода) выдается предупреждение.

Метод проверки Если в коде многократно выполняется dbms_lob.write, dbms_lob.writeappend, dbms_lob.append для CLOB/BLOB, либо многократно выполняется конкатенация ||,concat для varchar2, рекомендуется использовать специальную библиотеку конкатенации ::[RUNTIME].[CONCAT_LIB]. Она позволяет существенно увеличить быстродействие и снизить нагрузку на СП в DBI.
Пример ошибки

            begin
        loop
         dbms_lob.writeappend(...);
        end loop;
    end;
Пример исправления

            begin
        loop
         dbms_lob.writeappend(...);
         exit;
        end loop;
    end;
Отслеживание условных компиляций через команды в комментариях
COND_COMPILE_COMMENT
DBI

DBI стремится отказаться от использования Базы Данных при разработки приложений на платформе DBI, поэтому условные компиляции(#if/#elsif) с условиями требующими запуска для проверки значения запрещены.
Также могут быть запрещены все пользовательские условные компиляции, кроме числящихся в белом списке. Для этого у проверки есть 2 настройки с помощью которых можно включить такой более жесткий запрет, а также отредактировать список разрешенных define.
В условиях допускается оперирование define, например --#if R2 and not exists(DBI) - такой вид условной компиляции пропустится проверкой. Также пропустится сравнение результата системного макроса определяющего платформу компиляции со сторокой, вроде этого: &COMPILE$TARGET = 'DBI.PGS'

Иерархические запросы через connect by
CONNECTBY2WITH
DBI

При переходе на DBI версию приложения необходимо исключить использование Oracle специфической конструкции connect by позволяющей реализовать иерархические запросы. В ANSI SQL ближайшая аналогия это with (with recursive для PostgreSQl), соответственно необходимо либо переписать запрос на использование данной конструкции, либо отказаться от иерархических запросов. По таблицам модели данных иерархические запросы не работают, т.к. не поддержан синтаксис в Ignite.

Метод проверки В SQL выражениях производится поиск connect by

Обращение к данным из разных DAO в одном операторе
CROSS_DB_QUERY
DBI
Требование: необходимо подключение к Oracle схеме.

Прикладные данные и метаданные в проектах DBI располагаются в разных источниках, поэтому обращение к ним в одном операторе невозможно. К таким обращениям также неявно приводит использование модификаторов %classname, %classparent, %entity, %statename. Или разыменование ссылочных реквизитов на метаданные. Также в операторах с метаданными недопустимо обращение к таблицам varray.
Считается, что таблицы находятся в разных DAO в двух случаях:
1) В настройке проверки эти таблицы находятся в разных группах
2) Одна из таблиц отсутствует в настройке проверки, а другая - присутствует в любой из групп
По умолчанию для проверки задана одна группа - метаданные.
Вызов системным модификаторов или разыменование может трансформироваться в вычисление на этапе fetch sql, если удовлетворит правилам допустимого UDF, из основного это головной селект лист, без каких-либо трансформаций, подробнее в проверке на UDF. В таком случае join-а с системной таблицей не произойдет и проверка пропустит такие обращения.
Также на поведение данной проверки может неявно влиять настройка из проверки на UDF по учету временных кейсов, т.е. например один из таких кейсов, это UDF в ref курсорах, в них пока не поддержано вычисление UDF на этапе fetch, поэтому разыменование или системный модификатор удовлетворяющие всем ограничениям будут вызывать появление кросс-субд запросов.
Соответственно если производится адаптация на целевое состояние ТЯ, необходимо отключать контроль временных кейсов в проверке на UDF и включать настройку в текущей проверке разрешающую разыменовывать ссылки на метаданные. При проверке разыменований, которые могли бы потребовать добавить в запрос таблицу из метаданных, проверяется, что реквизит именно ссылка, а не разыменованная структура.

Поэтому запрещено анализировать текст ошибок в процедурном программном коде.

Альтернативы

  • Если нужно получить код ошибки, то используйте sqlcode, а не извлечение кода из текста ошибки;
  • Если нужно анализировать неизменную часть ошибки – используйте RUNTIME.PRINTFUN.SQLERRM_INF, это подходит скорее для прикладных исключений (APP_ERROR);

Контроль использования хинта на индекс
HINT_INDEX_ORDER_BY
DBI
Требование: необходимо подключение к Oracle схеме.

В запросах PostgreSQL с хинтом на индекс не работает сортировка данных, если она не указана явно. В Oracle же просходит неявная сортировка. Цель проверки - гарантировать, что не происходит неявной сортировки данных в случаях, когда порядок строк имеет значение. В ряде случаев, например, при использовании агрегатных функций или при выборке в конструкциях where in или exists, итоговый порядок не играет роли, и отсутствие явного order by допустимо.
В остальных случаях, необходимо, чтобы для всех колонок, составляющих индекс, в where или join присутствовали условия равенства, зафиксированные через сравнение с константой, переменной или параметром, и объединенные логическим оператором and. Таким образом, условия однозначно определяют значения колонок индекса и никакой сортировки не будет, так как поля будут иметь одни и те же значения.
Если в выборке присутствует order by или не удается найти указанный индекс на схеме, то ошибки не будет.

На случай ложного срабатывания можно указать комментарий над pragma, либо выборкой, содержащий следующий текст

hint указан для выбора индекса, а не для сортировки данных

Метод проверки В конструкциях select, for, locate, %locate, у которых указан хинт на индекс (в pragma или в комментарии), проверяется наличие order by. Если сортировки нет, то проверяется наличие агрегатных функций, контейнера where in, exists. Если и этого нет, то выдается ошибка в случае отсутсвия условий равенства на всех столбцах индекса в join или where.
Для корректной работы проверки необходимым условием является отсутствие синтаксических ошибок в проверяемых конструкциях.
Пример ошибки

            pragma hint('index_desc(a1 IDX_Z#FP_TUNE_VALH_COL_DATE)');
    for (select x(x.[VALDATE]:VALDATE) in p_arr) loop
        v_date := x.[VALDATE];
        exit;
    end loop;
Пример исправления

            pragma hint('index_desc(a1 IDX_Z#FP_TUNE_VALH_COL_DATE)');
    for (select x(x.[VALDATE]:VALDATE) in p_arr order by x.[VALDATE] desc) loop
        v_date := x.[VALDATE];
        exit;
    end loop;

Анализ размерности полей индексов.
INDEX_LENGTH
DBI

В PostgreSQL нельзя создать BTREE индекс с длинной индексируемого поля более 2704 байта при умолчательном размере блока 8кб. Ограничение в 2704 байта справедливо как для составного индекса, так и для индекса на одно поле. На размер поля оказывают влияние следующие факторы:

  • Текстовые поля по умолчанию сжимаются алгоритмом lz4 или pglz
  • Символы хранятся в UTF-8. Поэтому символ может занимать от 1 до 4 байт

Эти факторы не позволяет без анализа самого текста понимать, в каких случаях будет ошибка индекса, а в каких нет. В зоне риска находятся все индексы с общим размером текстовых полей более 676 символов ( 2704 / 4 ) . Другими типами данных пренебрегаем из-за их небольшого влияния. Например в 2704 байта поместится строка из

  • 1 300 рандомных букв только русского алфавита
  • 150 000 букв “w”

Вариантами решения могут быть:

Уменьшение размера поля; Исключение из индекса неиспользуемых полей; Переход на GIST индекс. Он убирает ограничение в 2704 байта. Он быстрее при поиске, но вставка данных будет медленнее. Также GIST индекс не поддерживает уникальность. Синтаксис описания находится во встроенной справке А2 по пути CFT Platform IDE Documentation > Элементы прикладной модели > Индексы > Аннотации @property для индекса и колонок индекса; Ничего не делать, если данные таковы, что размер строки индекса не превысит 2704 байта; И т.д.

Разработчик должен принимать решение исходя из знания, какие данных будут храниться в индексируемых полях

При переходе на DBI версию приложения необходимо использовать совместимые типы данных или их явные преобразования в конструкциях, результатом компиляции которых является SQL-операторы. Это связано с тем, что в различных диалектах SQL могут различаться правила неявного приведения типов и функции или специальный синтаксис для явного приведения.
У данной проверки есть 4 настройки:
- "Показывать предупреждения об ошибках определения типа" - данная настройка по умолчанию включена и говорит о том нужно ли проверке светить места где она не смогла определить тип. Светит она их принудительно с уровнем Warning вне зависимости от установленного уровня на проверке. Больше нужно для отладки, поддержки экзотических конструкций, но также может свидетельствовать об обращении к несуществующему объекту;
- "Раздельное хранение DATE и DATETIME" - если включить данную настройку, то проверка начнет различать указанные типы и разрешать инструкции вида <DATE> + <NUMBER>. Если же не установить данную настройку, то все объекты указанных типов по умолчанию будут принимать тип DATETIME, который транслируется в PostgreSQL как timestamp и не допускает операций <DATETIME> + <NUMBER>;
- "Пропускать ошибки связанные с разным хранением даты" - если включить данную настройку то проверка перестанет светить ошибки вида <DATETIME> + <NUMBER>; <DATETIME> - <DATETIME>;
- "Разрешить несовпадение типов для биндов" - не совпадение типов у биндов может компенсировать компилятор, поэтому если хочется править по минимуму можно включить данную настройку

Непубличные сущности, объявленные в операции, должны в ней упоминаться
NOT_MENTIONED
STYLE

Если объявленная сущность не упоминается в операции, то она должна быть удалена, так как не имеет смысла.
Проверка анализирует: непубличные функции/процедуры, параметры функций/процедур/операций, непубличные переменные, непубличные типы, переменные циклов, алиасы в цикле по выборке, составляющие параметров/переменных: поля записей, колонки переменных типа курсор.
Сообщения в большинстве случаев выводятся на описании/объявлении сущности, особенности:

  • если у функции/процедуры есть предописание, то сообщение выводится ещё и на нём

  • если алиас курсора не упоминается в цикле по нему, то сообщение выводится на объявлении переменной этого цикла

  • если в цикле по выборке алиас не упоминается, то на его объявлении выводится сообщение
    (если выборка содержит операции между select-ами верхнего уровня, то сообщение выводится только на первом select-е)

  • для параметров операции проверяется, упоминаются ли они в тексте операции;
    для операции типа "Отчет" дополнительно проверяется, упоминаются ли они в качестве report parameter;
    для операции типа "Фильтр" дополнительно проверяется, упоминаются ли они в формуле фильтра операции;
    если нигде из этих мест параметр не упоминается, то считается, что он не упоминается в коде;
    если параметр операции не упоминается в коде, то для операции с формой или использующей форму другой операции дополнительно проверяется, упоминается ли параметр операции в формулах фильтров параметров/переменных операции или на экранной форме (для операций типа печать первый по порядку параметр типа Memo/Clob игнорируется, т.к. он служебный) - если не упоминается, то считается, что параметр операции не упоминается

  • при проверке динамического PLP из проверки исключаются сущности, имена которых совпадают со служебными именами: для процедур/функций - "outer_vessel", "inner_vessel"; для переменных - "param", "result", "str_params", "clob_params", "blob_params" - если прикладной код использует такие имена, то сообщений для них не будет

  • если код содержит pragma if_def или управляющий комментарий #ifdef / #ifndef то при интерпретации сообщения <не упоминается> следует иметь в виду, что проверка "видит" только активные секции кода, и поэтому возможное упоминание в пассивной части кода игнорируется

  • если операция содержит указание USES или EXTENDS OF и вызов макроса BASE$EXECUTE или BASE$VALIDATE в секции execute/validate, то параметры такой операции исключаются из проверки

  • проверка может работать некорректно при наличии синтаксических ошибок, и/или ошибок линковки, и/или ошибок на форме

Контроль обработки исключений на предмет битой транзакции в PostgreSQL
OBLIGATORY_IN_OTHERS
DBI
Требование: необходимо подключение к Oracle схеме.

PostgreSQL в отличие от Oracle «портит» транзакцию при возникновении исключений большинства групп. О группах см. подробнее тут. После возникновения таких ошибок попытка выполнения любой команды SQL/DML будет сопровождаться исключением группы 25 – Invalid Transaction state, например,

25P02 - ERROR: current transaction is aborted, commands ignored until end of transaction block.

Проверка анализирует все блоки перехвата исключений и фильтрует по коду ошибки в соответствии с настройками:
- Безопасные коды исключений - по умолчанию все пользовательские коды исключений(–20 999 до –20 000) считаются безопасными, а с помощью данной настройки пропускаются следующие исключения: NO_DATA_FOUND(100), TOO_MANY_ROWS(-1422), VALUE_ERROR(-6502), COMPILE_ERROR(-6550), SNAPSHOT_TOO_OLD(-1555), ORACLE_DISCONNECT(-3114), PGA_AGGREGATE_LIMIT(-4036), END_OF_BODY(-29266), invalid LOB locator(-22275) и XML parsing failed(-31011), INVALID_PACKAGE_STATE(-6508), RESET_PACKAGE_STATE(-4061). Также в данный список можно внести код 600, который будет легализовывать other блок обработки исключения. Все остальные коды ошибок считаются ломающими транзакцию и требуют дополнительных экспериментов перед легализацией;
- Коды ошибок ломающие транзакцию - есть ошибки числящиеся за пользовательским диапазоном, но ломают транзакцию, к таким ошибкам ранее относился CANNOT_LOCK(-20500), сейчас блокировка выполняется с помощью инструкции skip locked и не приводит к поломке транзакции, но настройка осталась на случай выявления каких-то других исключений;
- Разрешить выход из блока обработки исключения по pragma error - данная настройка позволяет приравнять pragma error к raise для того, чтобы можно было итерационно приводить код в соответствие с данной проверкой;
- Не учитывать уровень вложенности при проверке на rollback и raise - т.е. проверка не бегает по коду рассматривая все возможные ветки ветвления кода как например проверка на закрытие файлов, а последовательно проверяет все инструкции. И для того, чтобы гарантировать что rollback или raise написаны корректно, нужно чтобы они находились на головном скоупе инструкций обработчика исключений. Включение данной настройки смегчает требование и пропускает код даже если rollback или raise находятся под if-ом.

В случае если исключение диагностируется как потенциально опасное, в блоке обработки исключения, производится поиск либо rollback, либо raise без каких-либо вложенностей в if-ы или подобные конструкции(регулируется настройкой), а также предшествующих конструкций, которые могут пойти в БД(будут описаны ниже). Т.е. если до rollback будет обнаружена не безопасная функция, например %parent и мы в блоке обработке исключения пойдем в БД, мы снова упадем доломав транзакцию и до rollback не доберемся. Поэтому только если анализ блока обработки исключения завершается успешным поиском одной из выше упомянутых конструкций, тогда анализ завершается и основной блок не анализируется на предмет возможной поломки.
Если мы нашли возможность доломать транзакцию или не нашли конструкций rollback и raise, то начинается анализ того, что вызывается в основном блоке, на предмет поиска обращений в БД. При нахождении первой попавшейся конструкции, которая может сходить в БД, выдается заключение о возможной поломке транзакции с просьбой обработать данный кейс.

Что считается обращением к БД

  • селекты,
  • dml операции,
  • commit,
  • обработка исключения DUP_VAL_ON_INDEX(-1) (из-за сброса кэша в БД),
  • динамика,
  • вызов функций/процедур/операций к коду которых плагин не может добраться или у которых отсутствует pragma restrict_references с флагами wnds и rnds. В частности, плагин не имеет доступа к коду PL/SQL пакетов.

Функции/процедуры/операции фильтруются по белому списку из настройки "Безопасные вызовы". Этот список рекомендуется пополнять только в случае невозможности установить прагму, например: PL/SQL пакеты или операции, которые нет возможности изменить.

Автономные транзакции

Функции/процедуры с автономными транзакциями в окончании имеют неявный commit (исключений не было) или rollback (исключения были). Это означает, что может сломаться только сессия самой автономки, на вызывающую сессию она влияния не оказывает. Поэтому для функций/процедур с автономными транзакциями проверка работает немного иначе:
- Безусловно считается, что вызов такой функции/процедуры не приведет к поломке транзакции - ни в основном блоке, ни в обработчике исключения;
- Предупреждение о возможности поломки транзакции внутри такой функции/процедуры возникает, если после блока перехвата или внутри блока перехвата есть обращение к БД до конструкций rollback/raise. Т.е. в отличии от обычных функций, отсутствие отката в блоке перехвата допустимо, если нет последующего обращения к БД до окончания функции.

        pragma error('Номер не уникален!');
    end;
Пример исправления

    begin
        &sp(SET)
        [NUM]  := P_NUM;
        [NAME] := P_NAME;

        &rb(SET)

Проверять sql на соответствие правилу расставления кавычек

У PostgreSQL и Oracle есть отличие в том, как производится поиск ссылочного объекта в SQL выражении. Т.е. имена таблиц, колонок или алиасов PostgreSQL перед исполнением переводит в нижний регистр, а Oracle - в верхний. Исключения составляют ссылки, обрамленные двойными кавычками: их имена остаются точно такими, как написано в SQL.
Также у PostgreSQL есть требование, что если в имени объекта содержится символ #, то он обязательно должен быть заключен в кавычки. В связи с этим, при миграции метаданных из Oracle в PostgreSQL, все имена таблиц, а также составные реквизиты создались в PostgreSQL в верхнем регистре.
С учетом вышесказанного мы получаем требование на добавление кавычек при обращении ко всем объектам, в именах которых есть символ #. Значение внутри кавычек должно быть в UPPER_CASE стиле.
Все остальные поля прикладных таблиц, а именно: ID, STATE_ID, SN, SU, CLASS_ID, COLLECTION_ID, C_ на текущий момент в PostgreSQL и Oracle имеют различный регистр, поэтому мы не имеем право их заключать их в кавычки. Соответственно их можно писать в любом стиле, Oracle возведет в верхний регистр и найдет такое поле, а PostgreSQL опустит в нижний регистр и тоже найдет такое поле.

Метод проверки Везде, где могут встретиться имена таблиц и колонок, производится проверка на соответствие ограничениям. Если в имени объекта отсутствует символ #, то допускается обращение как с кавычками, так и без, в противном случае выдается исключение.
Если встречается объект с именем ID, STATE_ID, SN, SU, CLASS_ID, COLLECTION_ID, начинающийся с C_ и заключенный в кавычки, проверка также ругается.
Пример ошибки

Пример исправления

            execute immediate 'truncate table "Z#ACCOUNT#ARC"';

Проверка на различное поведение регулярных выражений

В данной проверке предусмотрены настройки:
1) Отображать ли ошибки при наличии в регулярном выражении неизвестных частей.
2) Набор правил, которым должно удовлетворять регулярное выражение. По умолчанию настроены:

  • Поиск группы с пустым шаблоном ()* по номеру в функции regexp_instr. Пример: regexp_instr('abc def','()*def',1,1,0,'',1).
  • Использование метасимволов (\d, \s) в наборах символов. Пример: regexp_replace('sd\12 34\ds','([\s\d]+)', '<\1>').
  • Сверхжадная (ревнивая) квантификация. Пример: regexp_replace('abcccccc', '(ab)(c*+)(c)', '[\1]<\2>[\3]').
  • Квантификатор после ^ и $ ("^*", "^+", "^?", "$*", "$+", "$?"). Пример: regexp_replace('abc','^*','x').
  • Использование метасимволов \w и \W по причине различного поведения относительно русских букв. В замен можно использовать [[:alnum:]_] и [^[:alnum:]_], соответственно.
  • Не реализованные oracle-like Posix классы.
  • Поиск экранирования ] внутри шаблона символов с последующем нахождением за рамками шаблона символа ]. Пример: ^CHECK_ORDER\[[^\]]+]$

Аналоги Posix классов:

  • [:punct:] - [^ [:cntrl:][:alnum:]]
  • [:blank:] - [ \t]
  • [:graph:] - [^ [:cntrl:]]
  • [:word:] - [[:alnum:]_]

Также шаблон поиска проходит процедуру компиляции в java и при исключениях выдается предупреждение по данной проверке.

Проверять наличие схемы в DDL и grant/revoke
SCHEMA_IN_DDL
DBI

В PostgreSQL в отличии от Oracle, при создании объекта БД без указания схемы, объект будет создан на схеме, указанной первой в search_path, исключением является триггер, он наследует схему таблицы и поэтому при его создании схему указывать не нужно.
При выполнении команды модификации/удалении объекта без указания схемы, поиск объекта также будет производиться на схеме, указанной первой в search_path. Если не будет найден, PostgreSQL сгенерирует ошибку.
Настройка search_path частично определяется ЦФТ, частично банком и 100%, что схема с прикладными данными APP будет ниже в списке приоритетов, чем например схема SYS и BANK.
Поэтому , при выполнении DDL из прикладного кода, обязательно указывайте имя схемы. Пример - create table app.z#.....
Имя схемы app может быть изменено, поэтому использовать это имя как константу нельзя.

Использование операторов оконных функций специфичных только для Oracle
SELECTANALYTICARGUMENT
DBI

В ANSI SQL не поддержаны конструкции в функции ANALYTIC:
- keep
- within group - в PostgreSQL есть, но имеет другое значение.

Так же в стандарте SQL определены параметры RESPECT NULLS или IGNORE NULLS для функций lead, lag, first_value, last_value и nth_value. В PostgreSQL такие параметры не реализованы: эти функции ведут себя так, как положено в стандарте по умолчанию (или с подразумеваемым параметром RESPECT NULLS). Также функция nth_value не поддерживает предусмотренные стандартом параметры FROM FIRST и FROM LAST.

Метод проверки В первом параметре функции analytic производится поиск ключевых фрах lead, lag, first_value, last_value и nth_value.
Во втором параметре функции analytic производится поиск ключевых фраз: "keep", "within group", "ignore nulls", "respect nulls", "from first", "from last".
"keep" и "within group" вызывают срабатывание проверки вне зависимости от наличия ключевых слов в первом параметре функции analytic.
"ignore nulls" и "respect nulls" вызывают срабатывание проверки при нахождении в первом параметре функции analytic любой из ключевых фраз.
"from first" и "from last" вызывают срабатывание проверки при нахождении в первом параметре функции ключевой фразы "nth_value".

Проверка size-модификатора при сравнении с 0 или 1

JAVA PLSQL

Логика указанных ниже выражений – определить, есть ли записи вообще или нет.

  • %size(0) = 0 и %size(null) = 0
  • %size(0) > 0 и %size(null) > 0
  • %size(0) >= 0 и %size(null) >= 0
  • %size(0) <> 0 и %size(null) <> 0
  • %size(0) != 0 и %size(null) != 0
  • %size(0) < 0 и %size(null) < 0 – это хоть и бессмысленное (потому что оно всегда ложно), но всё-таки, расчет кол-ва ведется, а нам от него надо избавиться по логике

  • %size(0) < 1 и %size(null) < 1

В этих случаях подсчет всех записей не требуется, достаточно ограничиться одной строкой.

Контроль использования функций пакетов (UDF, ТЯ, Oracle) в select
UDF
DBI JAVA PLSQL
Требование: необходимо подключение к Oracle схеме.

Для DBI данное предупреждение является критичным, т.к. когда СП отправит в БД запрос на селект с обращением к какому-то бы то ни было пакету(Oracle, пользовательскому(UDF) или ТЯ), исполниться он не сможет по причине отсутствия пакетов.
А для JAVA и PL/SQL это скажется на переключении контекста м/у SQL и PL/SQL что не хорошо для производительности.

Но есть исключения и если вызов функции им удовлетворяет, то он вычисляется во время fetch-а курсора и тогда код будет работать. Но нужно понимать что если это будет касаться представлений, то такие вычисления наложат на представление ограничения фильтрации и сортировки по таким полям, как в интерфейсе, так и программно.
В качестве программной фильтрации подразумевается наложение условий в операции фильтра, или использование таких колонок в качестве условий переходов, или фильтры параметров и переменных. Т.е. для представлений хоть и возможен fetch лучше его избегать.

Правила которым должен удовлетворять UDF, чтобы вычисляться во время fetch-а:
- верхний селект лист - никаких преобразований над результатом вычисления функции - не допустимы селекты с union/minus/intersect на верхнем уровне - простые и групповые операции не могут исполниться во время fetch-а

Дополнительные особенности

1) %value, %arch - генерируется как UDF;
2) %classname, %classparent, %entity, %statename - могут стать UDF-ом исполняемым во время fetch если удовлетворят условиям выше, в противном случае преобразовываются в join-ы с таблицами метаданных(это другое ограничение Кросс-СУБД запросов);
3) Разыменования метаданных вида: x.[METHOD].[NAME] также может превратиться в UDF исполняемым во время fetch. Логика точно такая же как с модификаторами из предыдущего пункта;
4) Функциональные реквизиты без SQL реализации использованные в запрещенных для вычисляемых во время fetch местах, также светятся данной проверкой.

Если функция не зависит от данных в SQL, то ее исполнение переходит в bind и никаких проблем с такими конструкциями нет.

Есть временные не доработки компилятора, которые не позволяют UDF-у стать fetch-ем:
1) При использовании функций в конструкциях ref cursor они ни при каких обстоятельствах не переходят в fetch(https://jirabs.ftc.ru/browse/PLATFORM-46549)
2) Модификация параметров функций разрешена только с совместной передачей хотя бы одного не модифицированного параметра. Есть задача исключение такого ограничения(https://jirabs.ftc.ru/browse/PLATFORM-44045)
3) Вычисляемой колонкой не будет операция у которой есть архивный пакет(https://jirabs.ftc.ru/browse/PLATFORM-46328), актуально только для процедурного кода, в представлениях такой ошибки нет
4) Если в вызове функции явно указаны параметры как p_param == value, то такой вызов будет считаться некорректным и скомпилируется в вызов пакета(https://jirabs.ftc.ru/browse/PLATFORM-43786)

В DBI нельзя оперировать системными кодами исключений зарезервированными СУБД, т.к. они разные для Oracle и PostgreSQL.
Системными исключениями считаются все коды за пределами пользовательского диапазона(-20000..-20999).

- zero_divide(-1476)
- numeric_value_out_of_range(-1438)
- string_value_out_of_range(-12899)
- too_many_rows(-1422)
- no_data_found(100)

- resource_wait(-20500)
- parent_key_not_found(–2291)

Контроль переопределения размерности строкового выражения в рекурсивном запросе
VERIFY_TYPE_IN_WITH
DBI

PostgreSQL в рекурсивных запросах тип колонки берет из не рекурсивной части, т.е. первого select-а. Если в данном SQL будет использован вывод какой-нибудь колонки из таблицы со строковым типом ограниченной длины, то PostgreSQL будет контролировать, чтобы в рекурсивной части он не мог получить строку большей длины. Как разработчики описывают данный контроль в комментарии к коду:

/*
* Verify that the previously determined output column types and
* collations match what the query really produced.  We have to check
* this because the recursive term could have overridden the
* non-recursive term, and we don't have any easy way to fix that.
*/

Применение каких-либо модификаций с использованием функций или конкатенации указывает на то что в результате может получится строка неизвестной длины, единственным обнаруженным исключением пока является функция coalesce.
Например, на вот такой SQL:

WITH RECURSIVE recur(c_name, lvl) AS (
    SELECT 'test'::varchar(255) as c_name, 1 as lvl 
  UNION ALL
    SELECT a.c_add || g.c_name, g.lvl + 1
    FROM recur g, (select 'append' c_add) a
   where g.lvl < 2
)
SELECT * FROM recur;

PostgreSQL вернет ошибку: SQL Error [42804]: ERROR: recursive query "recur" column 1 has type character varying(255) in non-recursive term but type character varying overall

Допустимые префиксы и постфиксы, для локальных ТБП, реквизитов, методов и представлений
WRONG_LOCAL_PREFIX
STYLE

Локальные объекты должны иметь в коротком и полном наименовании один из задаваемых настройкой локальных префиксов. Может быть несколько пар префиксов для короткого наименования и полного. При этом для разных префиксов короткого наименования могут быть одинаковые префиксы полного наименования. Объекты для которых выполняется проверка:
- Локальные типы;
- Локальные атрибуты в дистрибутивных типах;
- Локальные операции в дистрибутивных типах;
- Локальные представления в дистрибутивных типах.

По умолчанию в настройке присутствует "VND_,ВНД. " для временных объектов внедрения. Для корректной работы проверки локальных объектов необходимо в общей настройке плагина "Файлы описания приложений" задать файлы описаний приложений (*.xsap). Обычно нужно 2 файла: ядерные приложения (например, core_7.6.10.xsap) и "ЦФТ-Банк Каталог Приложений" (cft_bank_22_4.xsap). При отсутствии хотя бы одного корректного файла описания приложений все объекты считаются дистрибутивными. В качестве ссылки на файл допускается указывать путь в формате URL.

Если не включена настройка "Требовать префикс для расширений", то расширения операций и представлений должны иметь в коротком и полном наименовании один из задаваемых настройкой постфиксов. Может быть несколько пар постфиксов для короткого наименования и полного. При этом для разных постфиксов короткого наименования могут быть одинаковые постфиксы полного наименования. При этом нет проверки на дистрибутивность расширяемой операции.
По умолчанию в настройке присутствует "_EXT,(расширение)", "_EX,(расширение)", "_E,(расширение)"

Если настройка "Требовать префикс для расширений" включена, то для расширений операций и представлений действуют такие же правила наименования, как и для остальных локальных объектов.
