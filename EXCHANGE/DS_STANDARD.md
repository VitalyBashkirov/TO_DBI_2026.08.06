# DS_STANDARD — Стандарт оформления DS-заданий

**Версия:** 1.0 от 19.09.2026
**Назначение:** единый шаблон для всех DS-заданий. Сокращает объём каждой задачи в 3–5 раз.

---

## 1. Стандартная шапка

```
**Дата:** <ДД.ММ.ГГГГ>
**Автор:** DeepSeek
**Исполнитель:** KODA
**Тип:** <разведка | реализация | уточнение | feature>
**Приоритет:** <высокий | средний | низкий>
**Зависит от:** <DS_XXX или «нет»>
**Блокирует:** <DS_XXX или «—»>
```

---

## 2. Стандартные ограничения

Действуют по умолчанию, если в задаче не указано иное:

- Не коммитить без команды `GIT`.
- Не менять файлы вне списка «Что менять».
- Не трогать тесты вне указанного списка.
- Соблюдать протоколы DS_048/049/050/052.
- Запись в `EXCHANGE\bot.log`:
  `[ДД.ММ.ГГГГ ЧЧ:ММ:СС] DS XXX: <краткий итог>.`
- Отчёт — в `EXCHANGE\OUTBOX\DS_XXX_<краткое_описание>_report.md` (см. §3.2), UTF-8 без BOM.
- Если при реализации выявится расхождение с предположениями задачи — остановиться, доложить автору DS, не додумывать.

## 3. Стандартный формат отчёта

Если в задаче не указано иное, отчёт содержит **6 разделов**:

```
# DS_XXX — Отчёт

## 1. Что сделано
- <краткий перечень>

## 2. Изменённые файлы
- <путь> — <что изменено>

## 3. Результат тестов
- Тесты: N/N PASSED
- Регресс DS_032–DS_XXX: <результат>

## 4. Расхождения
- <если есть; иначе «нет»>

## 5. Проверка
- Select-String / BOM / git log / pytest

## 6. Артефакты
- <пути>
```

Расширенная структура — если задача специфична (разведка, feature с UI и т.п.). В этом случае в задаче указываются дополнительные разделы.

### 3.1. Язык отчёта

Отчёт пишется на РУССКОМ языке (кириллица).

ЗАПРЕЩЕНО:
- Транслит (Vypolneno, Fail perenesen, Protokol zaversheniya).
- Смесь латиницы и кириллицы в русских предложениях.
- Английский язык в описаниях.

РАЗРЕШЕНО (латиница):
- Имена файлов, пути, команды.
- Названия технологий, API, функций (Popen, git, pytest).
- Код в блоках ```...```.

Согласовано с AGENTS.md, раздел «Формат записей в bot.log
(DS_050)»: там требование кириллицы для записей лога.

### 3.2. Имена файлов отчётов KODA

Отчёты KODA размещаются в `EXCHANGE\OUTBOX\` и именуются по шаблону:

**`DS_XXX_<краткое_описание>_report.md`**

где:
- `XXX` — номер DS (например, `103`, `108`, `109`),
- `краткое_описание` — латиница, `snake_case`, без пробелов
  (например, `gui_manual_run`, `gui_fixes_rescan_ui`, `final_gp`),
- `_report` — обязательный суффикс отчёта.

**Примеры:**
- `DS_103_gui_manual_run_report.md`
- `DS_108_gui_fixes_rescan_ui_report.md`
- `DS_109_report_naming_convention_report.md`

**Задания DS (исполненные)** переносятся KODA в `EXCHANGE\PROCESSED\`
с тем же базовым именем, но **без** суффикса `_report`:
- `DS_103_gui_manual_run_report.md` (отчёт) → `DS_103_gui_manual_run.md` (задание).
- `DS_108_gui_fixes_rescan_ui_report.md` (отчёт) → `DS_108_gui_fixes_rescan_ui.md` (задание).

**ЗАПРЕЩЕНО:**
- Имена без краткого описания: `DS_XXX_report.md`.
- Транслит: `DS_XXX_отчет.md`, `DS_XXX_otchet.md`.
- Пробелы в имени файла.

**Область применения:** с DS_109 вперёд. Исторические отчёты
(`DS_100a_report.md`, `DS_101*`, `DS_102_report.md`, `DS_104_report.md`,
`DS_105_report.md`, `DS_107_report.md`) **не переименовываются** —
во избежание разрыва ссылок в `bot.log` и `PROCESSED`.


**Плоский формат для INBOX-заданий (DS_125):**
При копировании .md-задания через Text Copy Download вложенные блоки
кода (три бэктика) ломают разметку — внешний блок "съедает" внутренние.
Решение: для тел заданий использовать плоский формат — отступы (4 пробела)
вместо вложенных блоков кода. Тело задания в OUTBOX/PROCESSED — плоский текст.

## 4. Стандартный шаблон «Разведка»

```markdown
## Разведка (стандарт)

1. Найти: <что> — где <каталоги/файлы>.
2. Собрать: <что именно> (определение, вызовы, контекст).
3. Воспроизвести: <баг/поведение> — <как>.
4. Зафиксировать: diff, MD5, факты.
5. Восстановить: если что-то менялось в ходе разведки.
6. Отчёт по стандарту (раздел 3) + дополнительные разделы (если указаны).
```

В задаче указываются отличия от шаблона: что искать, что воспроизводить.

### 6.1. Кодировка файлов и BOM

**Правило:** для файлов, которые читает Python/pytest/любой не-Windows-парсер, — **UTF-8 без BOM**.

| Расширение | Кодировка | Инструмент PowerShell |
|-----------|-----------|----------------------|
| `.py`, `.ini`, `.cfg`, `.json`, `.yaml`, `.toml` | **UTF-8 без BOM** | `[System.IO.File]::WriteAllText(..., UTF8Encoding($false))` |
| `.md`, `.log`, `.txt` (отчёты) | UTF-8 без BOM | `Set-Content -Encoding UTF8` (BOM допустим) |
| `.cmd`, `.bat` | ASCII / OEM | `Set-Content -Encoding ASCII` |

**Почему:** PowerShell 5.1 `Out-File -Encoding UTF8` **всегда** добавляет BOM (`EF BB BF`). Python, pytest, `.ini`-парсеры **не понимают** BOM → ошибки:

```
ERROR: F:\TO_DBI\pytest.ini:1: unexpected line: '\ufeff[pytest]'
```

**Правильно (PowerShell 5.1, без BOM):**

```powershell
[System.IO.File]::WriteAllText('F:\TO_DBI\pytest.ini', @"
[pytest]
testpaths = SRC/tests
"@, [System.Text.UTF8Encoding]::new($false))
```

**Правильно (UTF-8 с BOM допустим — для отчётов):**

```powershell
@"
# Отчёт
"@ | Set-Content -Encoding UTF8 F:\TO_DBI\EXCHANGE\OUTBOX\DS_XXX_<краткое_описание>_report.md
```

**Проверка BOM:**

```powershell
Format-Hex -Path F:\TO_DBI\pytest.ini | Select-Object -First 1
```

**Чтение bot.log:**

`bot.log` содержит кириллицу. PowerShell 5.1 `Get-Content` без явного
`-Encoding` читает файл как OEM/Windows-1251 → кириллица отображается
кракозябрами (например, `Р—Р°РїРёСЃР°РЅР°` вместо `записана`).

**Правило:** всегда использовать `-Encoding UTF8` при чтении `bot.log`:

```powershell
Get-Content -Path 'F:\TO_DBI\EXCHANGE\bot.log' -Encoding UTF8 |
    Select-Object -Last 5
```

При записи (`AppendAllText` с `UTF8Encoding($false)`) BOM отсутствует —
это корректно для append-режима (BOM только в начале файла). При чтении
явный `-Encoding UTF8` обязателен.

**Первые 3 байта:**
- `EF BB BF` — **BOM есть** (плохо для `.py`/`.ini`/`.json`).
- Иначе — **BOM нет** (хорошо).

**Случаи в проекте:**
- DS_089a — BOM fix (git log).
- DS_091a — `pytest.ini` BOM сломал парсинг.
- Правило — **обязательное** для всех будущих DS.


**ИСКЛЮЧЕНИЕ (Урок I, DS_126):** файлы `.ps1` с кириллицей должны
записываться **С BOM** (UTF-8 with BOM, EF BB BF). Причина — PS 5.1
читает .ps1 без BOM в системной ANSI (CP1251) и ломает кириллицу.
Для .py / .md / .json / .ini / .sql правило «UTF-8 без BOM» сохраняется.
### 6.2. Техника сводных блоков PowerShell (ручной запуск)

Сводный блок — это набор команд PowerShell, который KODA/пользователь
вставляет в консоль **одной вставкой** и запускает одной кнопкой.

**Обязательные элементы (см. также §2 и §6.1):**

0. **`Set-Location -LiteralPath 'F:\TO_DBI'`** + `Write-Host "Текущий каталог: $(Get-Location)"`
   — первой командой после `chcp`, для контроля CWD (урок чата 16).
1. **Команда 0 — кодировка** (первой строкой):
   ```powershell
   [Console]::OutputEncoding = [System.Text.Encoding]::UTF8
   $OutputEncoding = [System.Text.Encoding]::UTF8
   chcp 65001
   ```
2. Секции с заголовками: `# --- N. <назначение> ---`.
3. Готовность к одной кнопке (без промежуточного ввода).
4. Ожидание — таблицей **вне** блока.
5. Чтение — `-Encoding UTF8`; запись .py/.ini/.json/.md —
    `[System.IO.File]::WriteAllText(..., UTF8Encoding($false))`.

**Опциональный элемент (по необходимости):**

6.2.X. **Опциональная проверка кодировки (`$OutputEncoding.BodyName`)** — НЕобязательно

По желанию — после установки кодировок можно вывести фактическое имя
активной выходной кодировки для диагностики:

    [Console]::OutputEncoding = [System.Text.Encoding]::UTF8
    $OutputEncoding = [System.Text.Encoding]::UTF8
    Write-Host "OutputEncoding.BodyName: $($OutputEncoding.BodyName)"

Ожидаемое значение при корректной настройке: utf-8 (или utf8).
Данный пункт НЕ является обязательным элементом сводного блока.
Вставлять его — на усмотрение автора DS. В предполётные и верификационные
блоки по умолчанию НЕ включать.

**Запреты (проверено практикой, чат 15):**

1. **`return` в ручных блоках** — непредсказуем при интерактивной вставке,
   может завершить весь блок. Сломал первый запуск DS_112.
   **Не использовать.** Для выхода — `if (...) { <действие> } else { <действие> }`
   без `return`.

2. **`@"..."@` (here-string) с бэктиками, кавычками или кириллицей** —
   парсер не закрывает строку, консоль «зависает». Сломал второй запуск DS_112.
   **Не использовать.** Для записи многострочного текста — `-join` массив строк:
   ```powershell
   $lines = @(
     '# Заголовок',
     '',
     'Текст с кириллицей и "кавычками".'
   )
   $text = $lines -join "`r`n"
   [System.IO.File]::WriteAllText($path, $text, (New-Object System.Text.UTF8Encoding($false)))
   ```

3. **`Get-ChildItem` + `Format-Table`** — отложенный вывод, сбивает с толку.
   Правильно: `Write-Host "$($_.Name)"` или явный `Out-String`.

4. **`$LASTEXITCODE` после `Select-String`** — не работает для «нашёл/не нашёл»:
   `Select-String` всегда возвращает 0.
   Использовать `-match` / `Out-String` + проверку переменной:
   ```powershell
   $found = Select-String -Path $file -Pattern $pat -Encoding UTF8
   if ($found) { Write-Host "НАЙДЕНО" } else { Write-Host "НЕ НАЙДЕНО" }
   ```

5. **Большие блоки дробить** на маленькие шаги с проверкой после каждого:
   `Select-String` / `Test-Path` / `Write-Host`.

6. **BOM-check / git-операции / `Select-String` без предварительного
   `Set-Location` в корень проекта** — читается не тот файл (урок чата 16).

**Git-гигиена (связано):**

7. **`git add` — только прямые слэши** (`/`). Обратные (`\`) дают `fatal pathspec`.
8. **После переноса INBOX → PROCESSED** — проверять `Test-Path` в PROCESSED.
9. **DS-задание может оказаться в OUTBOX вместо INBOX** — проверять
   фактическое расположение перед переносом.

### 6.2.1. Практические грабли PowerShell (DS_125)

1. **-SimpleMatch не понимает |**
   ПЛОХО: Select-String -Pattern 'a|b' -SimpleMatch  (ищет буквальную строку "a|b")
   ХОРОШО (regex, без -SimpleMatch): Select-String -Pattern 'a|b'
   ХОРОШО (два вызова): Select-String -Pattern 'a' -SimpleMatch; Select-String -Pattern 'b' -SimpleMatch

2. **Select-String находит docstring и сигнатуры, а не только вызовы**
   ПЛОХО: Select-String -Pattern 'bot=True' -SimpleMatch  (найдёт docstring L109 и сигнатуру L108)
   ХОРОШО: Select-String -Pattern 'bot=True)' -SimpleMatch  (только вызовы)

3. **[System.IO.File]::ReadAllBytes / WriteAllText — только абсолютные пути**
   ПЛОХО: $p = 'EXCHANGE\INBOX\file.md'; ReadAllBytes($p) -> DirectoryNotFoundException
   ХОРОШО: $p = (Resolve-Path -LiteralPath 'EXCHANGE\INBOX\file.md').Path; ReadAllBytes($p)

4. **-Filter в Get-ChildItem не поддерживает regex-классы**
   ПЛОХО: Get-ChildItem -Filter 'DS_12[1-5]*'  (Filter не понимает [1-5])
   ХОРОШО (wildcard): Get-ChildItem -Filter 'DS_12*'
   ХОРОШО (Where-Object): Get-ChildItem | Where-Object { $_.Name -match '^DS_12[1-5]' }

5. **[Parser]::ParseFile и BOM (Урок H)**
   При ОТСУТСТВИИ BOM у .ps1 с кириллицей:
   - [Parser]::ParseFile читает файл в ANSI (CP1251) -> ложные ошибки.
   - [Parser]::ParseInput с ReadAllText(UTF8) -> 0 ошибок.
   Корень проблемы — не метод, а отсутствие BOM.
   ХОРОШО: обеспечить BOM у .ps1 (см. п.6).

6. **.ps1 с кириллицей требует BOM в PS 5.1 (Урок I)**
   PS 5.1 при запуске .ps1 БЕЗ BOM читает файл в системной ANSI
   (CP1251 на русской Windows). Кириллица -> кракозябры -> ложные
   ошибки парсинга ("Непредвиденная лексема }" на корректных строках).
   ХОРОШО: записывать .ps1 с кириллицей С BOM:
     $utf8WithBom = New-Object System.Text.UTF8Encoding($true)
     [System.IO.File]::WriteAllText($path, $text, $utf8WithBom)
   ПРОВЕРКА: $bytes = [IO.File]::ReadAllBytes($path)
             BOM = ($bytes[0] -eq 0xEF -and $bytes[1] -eq 0xBB -and $bytes[2] -eq 0xBF)

### п.7 (Урок J, DS_128): $matches в PowerShell — Hashtable, не массив

- $matches[0] — вся строка.
- $matches[1..n] — нумерованные группы (нумерация с 1).
- $matches[3] в -f-форматировании — НЕ работает как индекс группы.
- ПРАВИЛЬНО: именованные группы (?<name>...) + $($matches['name']).
- Или: "{0}-{1}" -f $matches[1], $matches[2] (индексы -f с 0,
  значения из $matches — с 1).
- ОПАСНОСТЬ: при ошибке форматирования внутри ForEach-Object строка
  может бесследно исчезнуть из потока. Всегда проверять
  «Строк до / после».

Пример:
  ПЛОХО: "[{3}-{2}-{1}]" -f $matches[3], $matches[2], $matches[1]
  ХОРОШО: "[$($matches['y'])-$($matches['m'])-$($matches['d'])]"

Получено на DS_128: первая попытка потеряла 7 строк из-за FormatError.
Диагностика выявила расхождение (462 вместо 469), файл восстановлен
из бэкапа и переделан.

### п.8 (Урок K, DS_128): аудит источника, не только симптома

Перед «нормализацией» данных (например, bot.log) — найти всех
писателей. Если источник жив, аномалии накапливаются снова.

Пример DS_128: план «нормализовать 35 строк без timestamp» был
неполным. Аудит выявил 8 мест в 6 файлах, которые до сих пор пишут
старым форматом. Миграция источника — в DS_129.



### 6.3. Порядок завершения DS

При завершении задачи DS_XXX соблюдать **жёсткую последовательность**
(см. AGENTS.md, раздел «Порядок завершения DS-задания»):

1. Выполнить правки по заданию DS.
2. Создать отчёт KODA в `EXCHANGE\OUTBOX\` (UTF-8 без BOM).
3. Перенести задание из `EXCHANGE\INBOX\` в `EXCHANGE\PROCESSED\`.
4. Записать строку в `EXCHANGE\bot.log` (формат DS_050, см. §6.1).
5. `git add` всех изменённых и новых файлов, включая:
   - файлы правок по заданию,
   - `EXCHANGE/bot.log`,
   - `EXCHANGE/PROCESSED/<задание>.md`,
   - `EXCHANGE/OUTBOX/<отчёт>.md`.
6. `git commit -m "<метка> Выполнено"`.
7. `git status -sb` → clean (кроме файлов из игнора).
8. `git push origin feature/dockerization`.
9. `git status -sb` → clean, ahead 0.

**ЗАПРЕЩЕНО:** создавать отчёт, переносить задание в PROCESSED или
писать в bot.log ПОСЛЕ `git add` / `git commit`. Любая из этих
операций после коммита оставляет хвост в рабочем дереве.

**Почему именно так:**

- Шаг 1 → шаг 3: если отчёт не написан, переносить нечего.
- Шаг 2 → шаг 3: лог содержит статус `DONE`/`ERROR`, который должен
  быть записан **до** физического перемещения файла. Иначе при сбое
  между переносом и логированием в логе не будет строки о выполненном DS.

**Типичные ошибки:**

- Сначала перенесли DS в PROCESSED, потом пишем лог → при сбое лог
  потеряется, файл уже не найдётся в INBOX.

### 6.4. Типовой результат DS

KODA обязан создавать EXCHANGE\OUTBOX\DS_<NNN>_result.md с полным выводом
команд в разделе ## 5. Проверка.

**Правило:** в DS_XXX_result.md раздел ## 5. Проверка содержит
вывод всех команд, перечисленных в DS в разделе ## 5. Проверка.

### 6.6. Логирование выполнения PS-блоков (DS_129)

Каждый сводный блок PowerShell запускается с Start-Transcript.
Лог пишется в F:\TO_DBI\PS\ (каталог не отслеживается git).
Файл перетаскивается в чат DeepSeek вместо копирования вывода.

- Каталог PS\ — в .gitignore (проверено в DS_129).
- Имя файла: ds<XXX>_<before|instead|after>_<YYYYMMDD_HHMMSS>.log.
- После успешного закрытия DS — логи можно удалять (не критичны).
- Правило 8 («Логи — только EXCHANGE\bot.log») относится к РАБОЧИМ
  логам, не к ОТЛАДОЧНЫМ транскриптам PS. Разделение явное.

Шаблон начала блока:
  $logDir = 'F:\TO_DBI\PS'
  if (-not (Test-Path $logDir)) { New-Item -ItemType Directory -Path $logDir | Out-Null }
  $ts = Get-Date -Format 'yyyyMMdd_HHmmss'
  $logFile = Join-Path $logDir "ds<XXX>_<этап>_$ts.log"
  Start-Transcript -Path $logFile -Force | Out-Null
  # ... команды ...
  Stop-Transcript | Out-Null


#### Стандартная шапка блока PS (DS_129)

Каждый блок начинается с:

    cls
    Set-Location -LiteralPath 'F:\TO_DBI'
    [Console]::OutputEncoding = [System.Text.Encoding]::UTF8
    $OutputEncoding = [System.Text.Encoding]::UTF8
    chcp 65001 | Out-Null
    cls

Первый cls — затирает предыдущий вывод PS ДО старта блока.
Второй cls — затирает «Active code page» от chcp.
Экран чистый: пользователь видит задание + лог выполнения.

Примечание: правило 0 регламента («Set-Location — первой командой»)
уточнено: cls идёт ПЕРЕД Set-Location.

#### §6.6.1. Логирование внешних процессов (Урок FF, DS_138b)

Start-Transcript в PowerShell 5.1 НЕ перехватывает stdout/stderr внешних
процессов (python.exe, git.exe, ollama.exe, node.exe и т.п.). Их вывод
не попадает в лог-файл транскрипта, даже если процесс отработал успешно
и вернул LASTEXITCODE=0.

Симптом: в логе транскрипта секции с вызовами внешних процессов выглядят
пустыми, хотя $LASTEXITCODE=0.

Решение: для каждого вызова внешнего процесса использовать явный
перенаправляющий конвейер:

    python tools\ai_local_worker.py --check 2>&1 | Out-Host
    git status -sb 2>&1 | Out-Host
    git log -1 --oneline 2>&1 | Out-Host

Правила:
- 2>&1 склеивает stderr в stdout.
- | Out-Host гарантирует попадание в транскрипт (см. Урок V, правило 62).
- $LASTEXITCODE проверять сразу после вызова — он относится к последнему
  внешнему процессу, а не к Out-Host.

Расширяет Урок V (правило 62) и Урок T (правило 60).

#### §6.6.2. Запись в bot.log — когда обязательна (Урок GG, DS_138b)

Правило 29 («bot.log пишется ДО коммита») обязательно для DS, которые
МЕНЯЮТ КОД, ТЕСТЫ, КОНФИГИ или ПОВЕДЕНИЕ АРМ.

Для DS без изменения кода — гигиена, удаление файлов, чистка .bak_,
обновление документации, добавление отчётов — запись в bot.log
НЕ ОБЯЗАТЕЛЬНА. Решение принимает Автор DS, фиксирует в отчёте
(раздел «Результат» или «Артефакты»).

Признаки DS «без кода»:

- Не тронуты tools\, pytest.ini, .gitattributes, .gitignore.
- Единственные изменения — в EXCHANGE\ (отчёты, задания, документация).

Во всех прочих случаях — bot.log обязателен.

#### §6.6.3. Fail-fast return в PS-блоках (уточнение правила 19, DS_138b)

Правило 19 («никаких return в ручных блоках PowerShell») действует
для нормального хода выполнения блока. Исключение — fail-fast guard:

Допустимо использовать return в PS-блоке, если ВСЕ условия выполнены:
- return находится ВНУТРИ ветки if ($условие_ошибки).
- Перед return выполнен Stop-Transcript | Out-Null.
- После return не остаётся полезной работы в этом блоке.
- return используется для остановки при обнаружении критичной ошибки
  (отсутствует артефакт, git add упал, commit не прошёл и т.п.).

Нельзя использовать return:
- В нормальном ходе (не в ветке ошибки).
- Внутри циклов для пропуска итерации (для этого — continue).
- Внутри switch-веток для выхода из switch (для этого — break).

#### §6.6.4. Шум NativeCommandError в PS 5.1 (расширение Урока T, DS_138b)

PowerShell 5.1 помечает любой вывод внешнего процесса в stderr как
«NativeCommandError», даже если это не ошибка, а обычное предупреждение
(например, «warning: LF will be replaced by CRLF» от git add).

Признаки:
- CategoryInfo          : NotSpecified: (...) [], RemoteException
- FullyQualifiedErrorId : NativeCommandError

Это НЕ ошибка блока. Ориентир — $LASTEXITCODE (должен быть 0).

Не пытаться «исправить» такие сообщения через 2>$null — это скроет
и настоящие ошибки. Оставлять вывод как есть; смотреть только
$LASTEXITCODE.

#### §6.6.5. Обязательное логирование каждого PS-блока (DS_138b)

Каждый PS-блок, выполняющий работу (создание/правка файлов,
git-операции, диагностика, сканирование), ОБЯЗАН:

- начинаться с очистки PS\ (N7),
- содержать Start-Transcript -Path PS\<имя>.log -Force | Out-Null,
- заканчиваться Stop-Transcript | Out-Null с выводом пути к логу.

Исключение — тривиальные однострочные проверки (например, git status -sb).
Их можно выполнять без лога.

Обоснование: без транскрипта нельзя восстановить, что именно делал
блок; логи PS\ — единственная замена ручному пересказу KODA
(правило 25).

#### §6.6.6. Идемпотентность блоков, дописывающих текст (Урок HH, DS_138b)

Любой PS-блок, дописывающий текст в файл через AppendAllText /
Add-Content / WriteAllText, должен быть ИДЕМПОТЕНТНЫМ относительно
повторного запуска: два запуска не должны дублировать фрагмент.

Минимум:
- Перед записью — Select-String по сигнатуре (заголовок, номер §,
  уникальная строка).
- Если найдено — fail-fast (STOP), ничего не писать.
- Логировать результат проверки ([OK] отсутствует → пишем;
  [STOP] найдено → не пишем).

Иначе: случайный двойной запуск даёт дубль, который затем чинится
вручную (инцидент DS_138b, 2026-10-09).

#### §6.6.7. Границы блоков в .md: не полагаться на пустые строки (Урок II, DS_138b)

При автоматическом поиске границ фрагмента в .md-файле
(для замены/удаления) НЕЛЬЗЯ полагаться на «логически ожидаемое»
расположение пустых строк. В .md число пустых строк между абзацами
зависит от того, кто и как писал файл (AppendAllText, WriteAllLines,
ручная правка и т.п.).

Правило:
- Выводить ВСЕ строки вокруг предполагаемой границы (не только те,
  что должны совпасть).
- Проверять именно фактические индексы массива Get-Content.
- Если хотя бы одна проверка не совпала — fail-fast (STOP), файл
  не трогать.

Инцидент DS_138b, 2026-10-09: первый fix-блок остановился на
fail-fast из-за неверного предположения о наличии пустой строки
между $LASTEXITCODE. и ---. Файл не пострадал.

#### §6.6.8. Формат записей в bot.log — копировать из последних строк (Урок JJ, DS_138c)

Перед append в bot.log (или любой существующий лог) — ПРОЧИТАТЬ
последние 2-3 строки и скопировать их формат (квадратные скобки,
разделители, наличие времени).

Причина: append «по памяти» даёт запись в другом стиле, выпадающую
из журнала. Инцидент DS_138b: строка DS_138b записана как
"2026-10-09  DS_138b  Обновление ...", тогда как существующий формат —
"[2026-10-09 HH:MM] DS_XXX: текст".

Правило:
- Перед append — Get-Content -Tail 3.
- Скопировать фактический префикс (скобки, дату-время, двоеточие).
- Проверить идемпотентность: строки с этим DS_XXX ещё нет.
