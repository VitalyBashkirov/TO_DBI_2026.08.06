```
Строка 32:
..........................> vDateRep varchar2(10);		-- отчетная дата...
<v53.PROC.ID_SIZE.п.3.27>   vDateRep varchar2(20);		-- отчетная дата...
Строка 33:
...

Статистика по файлу:
  v53.PROC.ID_SIZE.п.3.27: 2
  plpcheck.BAD_PREFIX: 1
  ...
```

## 4. Шаги

### 4.1. Формат лога `save_scan_only_log`

1. **Режим:** `Режим: прогноз исправлений, без записи` → **`Режим: сканирование (прогноз исправлений, без записи)`**.
2. **PLAN:** заполнить **КР-кодами** сработавших правил через запятую.
3. **Блок «Прогноз:»** — добавить **перед** статистикой:
   ```
   Прогноз:
   Строка <N>:
   ..........................> <было>
   <КР>   <стало>
   ...
   ```
   **Алгоритм** — точно как в `DS_053_Уточнение_4` → «Ожидаемый лог (прогноз)» и в `DS_053_Детерминированный_фиксер.md` → раздел 4 («Строки лога»):
   - `..........................>` — выравнивание «было» (точки МД+1);
   - `<КР>` — код правила в угловых скобках;
   - выравнивание `<КР>` — до МД+2 (с пробелами);
   - для нескольких правил на одной строке — несколько пар `>` / `<КР>`.
4. **Статистика по файлу** — заменить `Спрогнозировано исправлений: 0` на:
   ```
   Статистика по файлу:
     <rule_code>: N
     ...
   ```
5. **Пояснение о правилах в `ignore`** — если часть правил в `ignore`:
   ```
   Правил в ignore (не автофиксятся): N
     <rule_code_1>
     <rule_code_2>
     ...
   ```

### 4.2. Перенос PlpCheck-правил из `ignore` в `regex`/`hybrid`

1. Открыть `5.RUBRICATOR_PARSER_SQL v5.json`.
2. Для правил из `scan_report_*` при PlpCheck (`bad_prefix`, `not_mentioned`, `prefix_type_in_var_name`, `wrong_method_syntax`, `code_in_comment`):
   - найти соответствующие записи (`PlpCheck.STYLE.PREFIXES.bad_prefix.*` и т.д.);
   - посмотреть `transform_type`;
   - **если `ignore`**, и есть **`transform`** / **`example_out`** / **`algorithmic_hint`** — **перенести** в `regex` или `hybrid`;
   - **если нет** данных для автофикса — **оставить `ignore`** (обоснование — в отчёте).
3. **Проверка:** после правки `scan_VVxVVx_*` при PlpCheck — **непустой PLAN**.
