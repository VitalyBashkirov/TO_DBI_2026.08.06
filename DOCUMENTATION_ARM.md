## 1. Обзор проекта

**АРМ «Адаптация под DBI»** — десктопное приложение с графическим интерфейсом (tkinter) для
автоматизированной миграции банковского кода **PL/Plus (Oracle)** на целевую платформу
**2MCA DBI (PostgreSQL)**.

Архитектура — **гибридная**:
- **Детерминированный слой (Python, ~80–90 %)** — механические трансформации: переименование
  переменных, обновление ссылок, удаление неиспользуемых, исправление классов и методов.
- **LLM-слой (KODA, ~10–20 %)** — сложные/многошаговые случаи, не покрываемые детерминированными
  правилами.

**Заказчик:** Народный банк. **Сроки:** 30.07.2026 – 09.08.2026.

```bash
cd F:\TO_DBI

```

### 3.2. Docker

```bash

# GUI-режим (Linux с X11)
docker run -it \
  -v $(pwd)/PATCH_IN:/app/PATCH_IN \
  -v $(pwd)/PATCH_OUT:/app/PATCH_OUT \
  -v /tmp/.X11-unix:/tmp/.X11-unix:ro \
  -e DISPLAY=$DISPLAY \

  -e MODE=headless \
  -e SRC_DIR=patch_WORK \
  -e DST_DIR=patch_WORK \
  -v $(pwd)/PATCH_IN:/app/PATCH_IN \
  -v $(pwd)/PATCH_OUT:/app/PATCH_OUT \
  -v $(pwd)/logs:/app/logs \
  to_dbi_arm
```

### 5.2. Этап 1 — Сканирование (`PLPlusScanner`)

1. Загрузка паттернов из рубрикатора (`4.RUBRICATOR_PROMPTS.json`).
2. Обход `.plp` файлов по glob-шаблону (рекурсивно).
3. Построчный анализ: regex-поиск проблемных конструкций.
4. Исключение совпадений в комментариях (`--`), строковых литералах (`'...'`),
   подсказках оптимизатора (`/*+ ... */`).
5. Многострочный анализ для правил `WHEN OTHERS`, `NATIVEID`, `NOT_MENTIONED`.
6. Формирование списка `Issue` с метаданными (правило, строка, код, теги).

### 5.3. Этап 2 — Исправление (`PLPlusFixer.fix_file()`)

Конвейер `fix_file()` (строки ~1394–1434 в `code_fixer.py`):

```
fix_file(file_path, issues)
  │
  ├── 1. Загрузка строк файла (UTF-8)
  ├── 2. Исправление параметров функций (iif → p_bCondition и др.)
  ├── 3. ДЕТЕРМИНИРОВАННЫЙ СЛОЙ:
  │     ├── _build_rename_map()        — карта {старое_имя → новое_имя}
  │     ├── _update_references()       — замена по границам слов
  │     │     └── _replace_outside_quotes()  — исключая строковые литералы
  │     │         (кроме &debug — там литералы обновляются)
  │     ├── _remove_unused_variables() — удаление неиспользуемых объявлений
  │     ├── _validate_fix()            — проверка отсутствия старых имён
  │     ├── _fix_wrong_methods()       — [str].get_str_par → ::[RUNTIME].[STR]...
  │     └── исправление class → ::[CLASS]
  ├── 4. (Опц.) LLM-слой — send_to_koda / process_koda_response
  └── 5. Запись исправленного файла + статистика
```

### 5.4. Детерминированный слой — методы

| Метод                              | Назначение                                             |
|------------------------------------|--------------------------------------------------------|
| `_extract_declared_variables()`    | Поиск объявлений переменных (без состояния, посимвольно) |
| `_determine_prefix()`              | Определение префикса по типу: `ref`→`r`, `record`→`rec`, `varchar2`→`v` |
| `_clean_meaning()`                 | Очистка смысла от плохих префиксов: `v_vVDateRep`→`DateRep` |
| `_build_rename_map()`              | Построение карты `{старое_имя: новое_имя}`             |
| `_update_references()`             | Глобальная замена по границам слов, исключая литералы  |
| `_replace_outside_quotes()`        | Замена вне одинарных кавычек                           |
| `_remove_unused_variables()`       | Удаление неиспользуемых объявлений (NOT_MENTIONED.п.4.8) |
| `_validate_fix()`                  | Проверка отсутствия старых имён в коде                 |
| `_fix_wrong_methods()`             | Исправление обращений к методам (WRONG_METHOD.п.4.14)  |

### 5.5. Пример работы детерминированного слоя

| Было                          | Стало                          | Правило                |
|-------------------------------|--------------------------------|------------------------|
| `class HOOK_BANK;`            | `class ::[HOOK_BANK];`         | WRONG_CLASS.п.4.12     |
| `v_lrLrBranch ref [BRANCH]`   | `v_rBranch ref [BRANCH]`       | BAD_PREFIX.п.4.3       |
| `lrecBrInfo &lib_cl.tp_rec…`  | `v_recBrInfo &lib_cl.tp_rec…`  | PREFIX_TYPE.п.4.4      |
| `P_PARAM ref [REPS_PARAMS]`   | `v_rParam ref [REPS_PARAMS]`   | PREFIX_TYPE.п.4.4      |
| `v_vVDateRep varchar2(10)`    | _(удалено — неиспользуемое)_   | NOT_MENTIONED.п.4.8    |
| `P_FILE_XML [STRING_1000]`    | `v_vP_FILE_XML [STRING_1000]`  | PREFIX_TYPE.п.4.4      |
| `[str].get_str_par(...)`      | `::[RUNTIME].[STR].get_str_par(...)` | WRONG_METHOD.п.4.14 |
| `&debug('P_PARAM.\[BRANCH\]='||P_PARAM...)` | `&debug('v_rParam.\[BRANCH\]='||v_rParam...)` | Ссылки в &debug обновляются |

## 7. Модули — состав и назначение

### 7.1. `analyzer/scanner.py` — `PLPlusScanner`

- `Issue` (dataclass) — модель проблемы: `file_path`, `line_number`, `issue_type`,
  `description`, `original_code`, `category`, `rubricator_code`, `tags`.
- `DEFAULT_PATTERNS` — встроенные паттерны (outer join, rownum, when others, PlpCheck.STYLE.*).
- `MULTILINE_RULES` — правила, требующие анализа блока кода.
- `_is_in_comment_or_string()` — исключение совпадений в комментариях/литералах.
- `_load_patterns_from_rubricator()` — загрузка паттернов из JSON-рубрикатора.

### 7.2. `analyzer/deep_scanner.py` — `DeepScanner`

- Углублённое сканирование с использованием AI-анализатора.
- Интеграция с `PLPlusAIAnalyzer` для сложных правил.

### 7.3. `analyzer/ai_analyzer.py` — `PLPlusAIAnalyzer`

- AI-анализ сложных конструкций, не покрываемых regex.
- Возвращает `AIAnalysisResult` с рекомендациями.

### 7.4. `fixer/code_fixer.py` — `PLPlusFixer`

- `FIXES` — словарь автоматических исправлений (regex find→replace) по типам проблем.
- `fix_file(file_path, issues)` — основной конвейер исправления.
- Детерминированный слой (методы перечислены в разделе 5.4).
- `parse_koda_response()` — разбор ответа LLM на код + журнал.
- `generate_changelog()` — генерация журнала изменений.
- `clean_output` — флаг подавления маркеров `--(*)` и `--OLD`.

### 7.5. `koda_prompts.py` — `KodaPrompts`

- `generate_full_fix_prompt(code, rules)` — полный промпт для KODA с правилами.
- `generate_clean_output_instruction()` — инструкция для чистого вывода (без маркеров).

### 7.6. `rubricator_prompts.py` — `RubricatorPrompts`

- `load()` — загрузка `4.RUBRICATOR_PROMPTS.json`.
- `search_code_in_file(file_path, code)` — поиск проблем по коду правила.
- `get_fix_prompt(code)` — получение промпта для исправления.
- `get_examples(code)` — примеры «было/стало».
- `generate_test_file(code, output_dir)` — генерация тестового `.plp` файла.

### 7.7. `rubricator_priority_mapping.py`

- `RUBRICATOR_PRIORITY_MAPPING` — словарь маппинга пунктов приоритизации → коды правил.
- 4 уровня приоритета (1 — критичный, 4 — низкий).

### 7.8. `utils/encoding_utils.py`

- Определение и перекодировка файлов (UTF-8, CP1251, Windows-1251).
- Автоматическое определение BOM.

## 8. Рубрикатор правил

### 8.1. Категории

| Категория         | Кол-во правил | Описание                                      |
|-------------------|---------------|-----------------------------------------------|
| SQL/DML           | 36            | Преобразование SQL-синтаксиса Oracle → ANSI   |
| Хранение (STOR)   | 16            | Типы данных, индексы, секционирование          |
| Процедурный (PROC)| 48            | PL/SQL → PLPlus процедуры                     |
| Интеграции (INT)  | 5             | Замена Oracle-пакетов на DBI-аналоги          |
| Кэширование (CACHE)| 14           | Настройка кэша Hibernate                      |
| Разработка (DEV)  | 17            | Ограничения разработки                        |
| Локальные (LOCAL) | 8             | Локальные объекты DBI                         |
| PlpCheck (STYLE)  | 16            | Стиль кода (опционально)                      |
| **Итого**         | **160–161**   |                                               |

### 8.2. Автоматические исправления (regex)

| Правило                         | Что делает                                    |
|---------------------------------|-----------------------------------------------|
| `v50.SQL.OUTERJOIN.п.1.1`       | `(+)` → `LEFT/RIGHT JOIN`                     |
| `v50.SQL.ROWNUM.п.1.2`          | `ROWNUM` → `FETCH FIRST`                      |
| `v50.SQL.DECODE.п.1.6.1`        | `DECODE` → `CASE`                             |
| `v50.SQL.HINTS.п.1.18`          | Удаление подсказок оптимизатора               |
| `v50.STOR.DATE.п.2.2`           | `DATE` → `DATE_TIME`                          |
| `v50.PROC.WHENOTHERS.п.3.5`     | Добавление `ROLLBACK`/`RAISE` в `WHEN OTHERS` |
| `v50.PROC.EXECUTE.п.3.3`        | Экранирование имён в `EXECUTE IMMEDIATE`      |
| `v50.PROC.MACROS.п.3.4`         | Удаление макросов `execute`/`process`         |

### 8.3. Детерминированные исправления (Python-слой)

| Правило                              | Что делает                                        |
|--------------------------------------|---------------------------------------------------|
| `PlpCheck.STYLE.BAD_PREFIX.п.4.3`    | Переименование переменных с плохими префиксами    |
| `PlpCheck.STYLE.PREFIX_TYPE.п.4.4`   | Добавление префикса типа (`v_r`, `v_v`, `v_rec`)  |
| `PlpCheck.STYLE.NOT_MENTIONED.п.4.8` | Удаление неиспользуемых переменных                |
| `PlpCheck.STYLE.WRONG_METHOD.п.4.14` | Исправление обращений к методам                   |
| `PlpCheck.STYLE.WRONG_CLASS.п.4.12`  | `class NAME;` → `class ::[NAME];`                 |

### 8.4. Hybrid-правила (требуют LLM или ручного исправления)

- `v50.SQL.CONNECTBY.п.1.8` — `CONNECT BY` → `WITH RECURSIVE`
- `v50.SQL.DECODE.п.1.6.1` (complex) — сложный `DECODE` → `CASE WHEN`
- `v50.PROC.WHENOTHERS.п.3.5` (multiline) — многострочный `WHEN OTHERS`
- Помечаются в коде комментариями `--NEW` для ручного исправления

## 11. Типичный сценарий работы

1. **Запуск:** `python SRC/gui_app.py`
2. **Настройка путей:** исходный — `PATCH_IN\patch_RV`, результат — `PATCH_OUT\patch_RV`
3. **Выбор правил:** отметить `v50` в дереве рубрикатора (+ опц. PlpCheck)
4. **Сканирование:** `F5` → список `Issue` с указанием строк и правил
5. **Исправление:** `F6` → детерминированный слой + (опц.) KODA
6. **Проверка:** просмотр исправленных файлов в `PATCH_OUT`
7. **Журнал:** вкладка «Changelog» / сохранение в `.md`
8. **Архивация:** при включённой опции — ZIP в `PATCH_OUT`
